# Abhängigkeiten über Interfaces

:::note[Lernziele]
- Du erklärst, was eine <Term id="dependency">Abhängigkeit</Term> ist und warum `new` in einer Klasse sie fest verdrahtet.
- Du kannst eine Abhängigkeit als Interface über den Konstruktor übergeben (<Term id="constructor-injection">Constructor Injection</Term>).
- Du kannst alle Objekte an einer Stelle zusammensetzen (<Term id="composition-root">Composition Root</Term>).
- Du erklärst, warum eine übergebene Abhängigkeit Tests einfacher macht.
:::

## Das Problem: `new` in der Klasse

Eine Klasse, die ein anderes Objekt benutzt, hat eine Abhängigkeit. Im Beispiel braucht `AlertService` einen `ConsoleSender`, um eine Nachricht zu senden. Die Klasse erzeugt ihn selbst mit `new`.

<CSharpRunner code={tightCoupling} />

<CodeBlock language="text" title="Ausgabe">{tightCouplingOutput}</CodeBlock>

Das Programm läuft, aber `AlertService` ist jetzt fest mit `ConsoleSender` verdrahtet. Drei Dinge folgen daraus:

1. Soll die Nachricht in eine Datei statt auf die Konsole gehen, musst du `AlertService` ändern.
2. Braucht `ConsoleSender` selbst etwas, muss `AlertService` es besorgen. Der Aufbau der Objekte verteilt sich über viele Klassen.
3. Ein Test kann den Sender nicht ersetzen. Jeder Test von `AlertService` schreibt auf die Konsole.

## Die Lösung: die Abhängigkeit von außen übergeben

Die Lösung hat zwei Teile. Erstens sagt `AlertService` nicht mehr, **welche** Klasse er braucht, sondern nur, **was** sie können muss: Er verlangt ein Interface (Modul 8). Zweitens erzeugt er das Objekt nicht selbst. Er nimmt es als Parameter seines Konstruktors entgegen und speichert es im Feld. Wer das `AlertService`-Objekt erzeugt, übergibt die Abhängigkeit. Das heißt <Term id="dependency-injection">Dependency Injection</Term> (DI, Abhängigkeiten übergeben), und diese Form heißt Constructor Injection.

Die Objekte werden an einer einzigen Stelle zusammengesetzt, am Anfang von `Program.cs`. Diese Stelle heißt Composition Root. Alle anderen Klassen rufen `new` für ihre Abhängigkeiten nicht auf.

Dahinter steckt eine Idee, die <Term id="inversion-of-control">Inversion of Control</Term> (Umkehr der Steuerung) heißt: Die Klasse bestimmt nicht mehr selbst, welche Abhängigkeit sie benutzt. Der Code, der sie erzeugt, entscheidet.

<summary>Lösung und Erklärung anzeigen</summary>

Die Ausgabe ist `SEND: bob failed 5 times` und danach `[ALERT] dave failed 3 times`. Die Erklärung folgt den Schritten, die du bei jeder Constructor Injection brauchst:

1. **Vertrag festlegen:** `IAlertSender` beschreibt, was ein Sender kann: `Send(string text)`.
2. **Abhängigkeit als Parameter nennen:** Der Konstruktor von `AlertService` verlangt einen `IAlertSender` und speichert ihn im Feld `sender`. In der Klasse steht kein `new` für den Sender.
3. **Objekte zusammensetzen:** Am Anfang des Programms entstehen `ConsoleSender`, `PrefixSender` und die beiden `AlertService`-Objekte. Das ist der Composition Root.
4. **Benutzen:** `Raise` ruft `sender.Send(…)` auf. Welche Klasse dahinter steckt, weiß `AlertService` nicht.

**Was passiert, wenn …** du `first` einen `PrefixSender` übergibst? Dann gibt die erste Zeile `[ALERT] bob failed 5 times` aus, und du hast `AlertService` nicht geändert.

</details>

<details>
<summary>Vertiefung: Dependency Inversion (optional)</summary>

Ohne Interface hängt `AlertService` im Quelltext von `ConsoleSender` ab. Mit Interface hängen beide vom Interface ab: `AlertService` benutzt es, `ConsoleSender` setzt es um. Die Abhängigkeit zeigt vom Detail zur Abstraktion. Dieses Prinzip heißt Dependency Inversion, und Dependency Injection ist die Praxis, die dadurch möglich wird ([Architectural principles: Dependency inversion](https://learn.microsoft.com/dotnet/architecture/modern-web-apps-azure/architectural-principles#dependency-inversion)). Ein weiteres Prinzip dort: Eine Klasse nennt in ihrem Konstruktor alles, was sie zum Arbeiten braucht (Explicit Dependencies).

## Achtung

:::warning[Achtung]
<Misconception id="m15-l01-di-needs-container" />

**„Dependency Injection gibt es nur mit einem Container.“** Das stimmt nicht. Sobald eine Klasse ihre Abhängigkeit im Konstruktor entgegennimmt und der aufrufende Code sie übergibt, ist das Dependency Injection von Hand. Ein Container, den du in der nächsten Lektion kennenlernst, nimmt dir nur die Arbeit ab, die Objekte zusammenzusetzen.
:::

:::warning[Achtung]
<Misconception id="m15-l01-interface-no-benefit" />

**„Ein Interface mit nur einer Implementierung bringt nichts.“** Das stimmt nicht. Der Nutzen zeigt sich, sobald eine zweite Implementierung nötig wird: im Test (ein Spy statt der Konsole) oder später im Betrieb (eine Datei statt der Konsole). Dann ändert sich nur der Composition Root, nicht die Klasse.
:::

## Zusammenfassung

Eine Klasse, die ihre Abhängigkeit mit `new` selbst erzeugt, ist an einen konkreten Typ gebunden. Bei Constructor Injection nennt sie die Abhängigkeit als Interface-Parameter ihres Konstruktors, und der aufrufende Code übergibt sie. Die Objekte setzt ein Composition Root am Anfang des Programms zusammen. Für einen Test übergibst du ein Test-Double. Dafür brauchst du keinen Container und keine Bibliothek.
