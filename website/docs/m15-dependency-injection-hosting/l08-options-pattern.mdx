# Das Options-Pattern

:::note[Lernziele]
- Du kannst einen Konfigurationsabschnitt an eine Options-Klasse binden und als `IOptions<T>` injizieren.
- Du unterscheidest `IOptions<T>`, `IOptionsSnapshot<T>` und `IOptionsMonitor<T>` nach Lebensdauer und Aktualisierung.
- Du validierst Optionen mit Attributen und einem Lambda und prüfst sie beim Start.
:::

## Eine Klasse für zusammengehörige Einstellungen

In `m15-l07` hat SecLog seine Schwellen mit `GetValue<int>("Detection:MaxFailures")` gelesen. Das funktioniert, aber der Schlüssel steht als Text im Code, und jede Stelle, die den Wert braucht, muss ihn selbst lesen. Das <Term id="options-pattern">Options-Pattern</Term> löst das mit einer Klasse: Sie steht für eine Gruppe zusammengehöriger Einstellungen, und eine Klasse, die diese Einstellungen braucht, verlangt nur diese Klasse ([Options pattern in .NET](https://learn.microsoft.com/dotnet/core/extensions/options)).

Eine Options-Klasse hat feste Regeln: Sie ist nicht abstrakt, hat einen öffentlichen Konstruktor ohne Parameter, und ihre Einstellungen sind öffentliche Eigenschaften mit `get` und `set`. Felder werden nicht gebunden. Standardwerte setzt du im Initialisierer der Eigenschaft (`m06-l06`).

Zwei Schritte machen aus einem Konfigurationsabschnitt eine Instanz:

1. **Binden:** `services.Configure<DetectionOptions>(configuration.GetSection("Detection"))` verbindet den Abschnitt mit der Klasse. Der Name des Abschnitts muss nicht der Name der Klasse sein.
2. **Injizieren:** Eine Klasse verlangt im Konstruktor `IOptions<DetectionOptions>` und liest die Einstellungen mit `.Value`. Das Objekt entsteht erst beim ersten Zugriff auf `Value`.

## Drei Interfaces, drei Lebensdauern

Der Container liefert die Optionen über drei Interfaces. Sie unterscheiden sich in Lebensdauer und Aktualisierung:

| Interface | Lebensdauer | Neue Werte nach dem Start |
| --- | --- | --- |
| `IOptions<T>` | Singleton | nein, die Werte werden einmal gelesen |
| `IOptionsSnapshot<T>` | Scoped | ja, für jeden Scope neu berechnet |
| `IOptionsMonitor<T>` | Singleton | ja, `CurrentValue` ist immer aktuell, mit Änderungsmeldungen |

Die Lebensdauern sind dieselben wie in `m15-l03` und `m15-l04`: Ein Singleton darf keinen Scoped-Service verlangen, also darf es auch keinen `IOptionsSnapshot<T>` verlangen. Ein Singleton, das neue Werte braucht, nimmt `IOptionsMonitor<T>` ([Options pattern in .NET: Options interfaces](https://learn.microsoft.com/dotnet/core/extensions/options#options-interfaces)).

Neue Werte entstehen in einer echten App, wenn sich eine Konfigurationsquelle ändert, zum Beispiel eine JSON-Datei, die mit `reloadOnChange: true` geladen wurde. Das Programm unten ändert den Wert selbst und lässt die Konfiguration mit `Reload()` neu lesen. Das ersetzt hier die Änderung der Datei.

## Optionen validieren

Falsche Werte in der Konfiguration (eine Schwelle von 0, ein Zeitfenster von −5 Minuten) sind ein typischer Fehler. Die <Term id="options-validation">Validierung</Term> prüft die Werte einer Options-Klasse:

- **Attribute** (`m14-l06`): `[Range(1, int.MaxValue)]` auf einer Eigenschaft beschreibt die erlaubten Werte. `ValidateDataAnnotations()` schaltet die Prüfung ein.
- **Lambda** (`m10`): `Validate(o => …, "Meldung")` prüft eine eigene Regel. Liefert das Lambda `false`, ist die Meldung der Fehler.
- **Fehler:** Eine fehlgeschlagene Prüfung wirft eine `OptionsValidationException`. Ihre Eigenschaft `Failures` enthält alle Meldungen.

Wann die Prüfung läuft, ist eine Frage der Wahl. Ohne weitere Angabe läuft sie, wenn die Optionen zum ersten Mal gebraucht werden. Mit `ValidateOnStart()` läuft sie beim Start des Hosts. Der Fehler fällt dann sofort auf und nicht erst mitten im Betrieb ([Options pattern in .NET: Options validation](https://learn.microsoft.com/dotnet/core/extensions/options#options-validation)).

Das Programm startet zwei Mal einen Host mit denselben ungültigen Werten (`MaxFailures` = 0, `WindowMinutes` = 100): ohne und mit `ValidateOnStart`. Der Host hier ist nur das Mittel, um den Start zu zeigen.

## Achtung

:::warning[Achtung]
<Misconception id="m15-l08-options-shows-current-value" />

**„`IOptions<T>` zeigt immer den aktuellen Wert der Datei.“** Das stimmt nicht. `IOptions<T>` ist ein Singleton und liest die Einstellungen einmal. Änderungen nach dem Start sieht es nicht. Dafür gibt es `IOptionsSnapshot<T>` (pro Scope) und `IOptionsMonitor<T>` (Singleton).
:::

:::warning[Achtung]
<Misconception id="m15-l08-invalid-options-fail-at-start" />

**„Ungültige Optionen lassen das Programm schon beim Start scheitern.“** Das stimmt nur mit `ValidateOnStart`. Ohne es läuft die Prüfung erst beim ersten Zugriff auf `Value`. Das Programm startet dann ohne Fehler und scheitert später.
:::

## Zusammenfassung

Eine Options-Klasse hat einen Konstruktor ohne Parameter und öffentliche Eigenschaften. `Configure<T>` bindet einen Konfigurationsabschnitt an sie, und eine andere Klasse verlangt `IOptions<T>`. `IOptions<T>` ist ein Singleton und liest einmal, `IOptionsSnapshot<T>` ist Scoped und rechnet pro Scope neu, `IOptionsMonitor<T>` ist ein Singleton mit dem aktuellen Wert. Attribute und `Validate` prüfen die Werte, eine Verletzung wirft eine `OptionsValidationException`. `ValidateOnStart` zieht die Prüfung auf den Start vor.
