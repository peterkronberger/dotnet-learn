## Der Container nimmt dir das Zusammensetzen ab

In der letzten Lektion hast du den Composition Root von Hand geschrieben: erst `ConsoleSender`, dann `AlertService(sender)`. Bei zehn Klassen mit Abhängigkeiten untereinander wird das lang. Ein <Term id="di-container">DI-Container</Term> übernimmt diese Arbeit. Du sagst ihm einmal, welcher Typ für welches Interface erzeugt wird. Danach erzeugt er die Objekte und füllt die Konstruktorparameter selbst.

In .NET gibt es dafür drei Schritte:

1. **Registrieren:** Du trägst jede <Term id="service-registration">Registrierung</Term> in eine `ServiceCollection` ein, zum Beispiel `AddSingleton<IAlertSender, ConsoleSender>()`.
2. **Bauen:** `BuildServiceProvider()` macht aus der Collection den Container, einen `ServiceProvider`.
3. **Holen:** `GetRequiredService<T>()` liefert ein Objekt vom Typ `T`.

<Forward concepts={['die Lebensdauern von Services (`AddSingleton`, `AddScoped`, `AddTransient`)']} module="15" />

In dieser Lektion benutzt jedes Beispiel `AddSingleton`. Die Unterschiede zwischen den Methoden folgen in der nächsten Lektion.

Die Pakete `Microsoft.Extensions.DependencyInjection` und `…Abstractions` liefern die Typen. Der Runner hat sie eingebaut.

<details>
<summary>Lösung und Erklärung anzeigen</summary>

Die Ausgabe ist `SEND: bob failed 5 times`, `GetService: null` und `GetRequiredService: InvalidOperationException`. Die Schritte:

1. **Registrieren:** `AddSingleton<IAlertSender, ConsoleSender>()` legt fest, dass für `IAlertSender` ein `ConsoleSender` entsteht. `AddSingleton<AlertService>()` registriert die Klasse selbst.
2. **Bauen:** `BuildServiceProvider()` erzeugt den Container. Er ist `IDisposable`, darum steht `using` davor.
3. **Auflösen:** `GetRequiredService<AlertService>()` erzeugt ein `AlertService`-Objekt. Der Container sieht den Konstruktorparameter `IAlertSender`, erzeugt den `ConsoleSender` und übergibt ihn.
4. **Fehlender Service:** Für `UnregisteredSender` gibt es keine Registrierung. `GetService<T>()` meldet das mit `null`, `GetRequiredService<T>()` mit einer `InvalidOperationException`.

**Was passiert, wenn …** du `AddSingleton<IAlertSender, ConsoleSender>()` weglässt? Dann kann der Container den Konstruktorparameter von `AlertService` nicht auflösen, und das Holen des `AlertService` scheitert.

</details>

## Mehrere Implementierungen eines Interfaces

Für dasselbe Interface darfst du mehrere Registrierungen eintragen. Der Container behandelt sie nach festen Regeln:

- Eine einzelne Anfrage (`GetRequiredService<IAlertSender>()` oder ein Parameter `IAlertSender`) bekommt die **zuletzt** registrierte Implementierung.
- Eine Anfrage nach `IEnumerable<IAlertSender>` (oder `GetServices<IAlertSender>()`) bekommt **alle**, in der Reihenfolge der Registrierung.
- `TryAddSingleton` registriert nur, wenn für das Interface noch nichts eingetragen ist.
- Eine Lambda (Factory) erzeugt das Objekt selbst. Du brauchst sie, wenn der Konstruktor Argumente verlangt, die der Container nicht kennt, zum Beispiel den Text `"[ALERT]"`.

:::info[Vorhersage]
Das Programm trägt `ConsoleSender` und danach `PrefixSender` ein (der zweite mit einer Lambda). Danach folgt ein `TryAddSingleton`. Wie viele Zeilen gibt es insgesamt, und welche Sender schreiben sie? Notiere deinen Tipp und führe den Code dann aus.
:::

Es sind sechs Zeilen. Die Schritte:

1. **Einzelne Anfrage:** `single` ist der zuletzt registrierte `PrefixSender`: `[ALERT] one sender requested`.
2. **Alle Registrierungen:** `GetServices` liefert `ConsoleSender` und `PrefixSender` in dieser Reihenfolge. Das `TryAddSingleton` hat nichts hinzugefügt, weil schon eine Registrierung existierte.
3. **Einzelner Parameter:** `AlertService` bekommt im Konstruktor einen `IAlertSender`, also den letzten, den `PrefixSender`: `[ALERT] One: …`.
4. **`IEnumerable`-Parameter:** `BroadcastService` bekommt alle Sender und ruft beide auf: eine `SEND:`-Zeile und eine `[ALERT]`-Zeile.

## Keyed Services

<Since dotnet="8" />

Manchmal soll ein Service genau eine bestimmte Implementierung bekommen und nicht die letzte. Dafür gibt es Keyed Services. Du registrierst mit einem Schlüssel (`AddKeyedSingleton<…>("console")`), holst mit `GetRequiredKeyedService<T>("console")` und wählst am Konstruktorparameter mit dem Attribut `[FromKeyedServices("prefix")]`. Das Attribut gehört zu den Attributen aus Modul 14: Es hat als Ziel einen Parameter. Der Schlüssel kann jedes Objekt sein, das `Equals` richtig umsetzt.

## Achtung

:::warning[Achtung]
<Misconception id="m15-l02-getservice-throws" />

**„`GetService` wirft eine Exception, wenn nichts registriert ist.“** Das stimmt nicht. `GetService<T>()` gibt in diesem Fall `null` zurück. Eine Exception wirft `GetRequiredService<T>()`. Wenn dein Code den Service unbedingt braucht, nimm `GetRequiredService<T>()`: Der Fehler tritt dann sofort auf und nicht erst später als `NullReferenceException`.
:::

:::warning[Achtung]
<Misconception id="m15-l02-container-finds-types" />

**„Der Container findet Implementierungen von selbst.“** Das stimmt nicht. Er kennt nur, was du registriert hast. Gibt es für ein Interface keine Registrierung, hat er nichts zu erzeugen. Darum steht in jedem Beispiel zuerst die Registrierung.
:::

## Zusammenfassung

Ein DI-Container erzeugt Objekte und löst Konstruktorparameter selbst auf. Du registrierst Services in einer `ServiceCollection`, baust mit `BuildServiceProvider()` den `ServiceProvider` und holst mit `GetRequiredService<T>()` (wirft bei fehlender Registrierung) oder `GetService<T>()` (liefert `null`). Mehrere Registrierungen für ein Interface sind erlaubt: Eine einzelne Anfrage bekommt die letzte, `IEnumerable<T>` bekommt alle, `TryAdd…` registriert nur, wenn noch nichts eingetragen ist. Eine Lambda erzeugt das Objekt selbst. Keyed Services wählen eine Implementierung über einen Schlüssel.
