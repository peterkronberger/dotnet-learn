## Zwei Übersetzungen

Dein Quelltext ist Text. Ein Prozessor kann ihn nicht ausführen. In .NET sind dafür zwei Übersetzungsschritte nötig ([Managed Execution Process](https://learn.microsoft.com/dotnet/standard/managed-execution-process)):

1. **Compiler:** Er übersetzt den Quelltext in <Term id="il">IL (Intermediate Language, Zwischensprache)</Term>. Microsoft Learn beschreibt IL als „CPU-independent set of instructions that can be efficiently converted to native code“. Dazu erzeugt der Compiler Metadaten, die zum Beispiel die Typen deines Programms beschreiben. IL und Metadaten stehen zusammen in der Programmdatei.
2. **<Term id="jit">JIT (Just-in-Time-Compiler)</Term>:** Er gehört zur <Term id="clr">CLR</Term> und übersetzt die IL erst, wenn das Programm läuft, in Maschinencode für den Prozessor. Die Quelle sagt: Eine Methode wird beim ersten Aufruf übersetzt, danach läuft der gespeicherte Maschinencode.

Der Maschinencode ist die erste Form, die der Prozessor direkt ausführen kann. Die CLR führt das Programm dann aus und bietet Dienste wie die automatische Speicherverwaltung.

## Compilerfehler und Laufzeitfehler

Weil der Compiler vor dem Start arbeitet, kann er manche Fehler schon dann melden. Solange ein <Term id="compile-error">Compilerfehler</Term> besteht, gibt es keine Programmdatei, die starten könnte. Ein <Term id="runtime-error">Laufzeitfehler</Term> dagegen bleibt unbemerkt, bis die betroffene Anweisung läuft. Alles davor ist dann schon passiert.

## Drei Ausführungsmodelle

Der JIT ist der Standard. Es gibt zwei Varianten, bei denen Maschinencode schon vor dem Start entsteht (<Term id="ready-to-run">ReadyToRun</Term> und <Term id="native-aot">Native AOT</Term>; AOT steht für Ahead of Time, „im Voraus“). Hier geht es nur um die Idee. Wie man sie einschaltet, kommt in Modul 14.

| Modell | Was steckt im Programm? | Start | Kompatibilität und Größe |
| --- | --- | --- | --- |
| **JIT zur Laufzeit** (Standard) | IL | Der JIT übersetzt beim Lauf. | Läuft auf jedem Rechner mit passender .NET-Laufzeit. |
| **ReadyToRun** | IL **und** vorab erzeugter Maschinencode | Weniger JIT-Arbeit beim Start. | Dateien werden größer, laut Quelle meist zwei- bis dreimal. Der JIT bleibt nötig, zum Beispiel für manche Methoden. |
| **Native AOT** | Nur Maschinencode (mit der nötigen Laufzeit darin) | Schnellerer Start, kein JIT. | Läuft ohne installierte .NET-Laufzeit, aber mit Einschränkungen: zum Beispiel kein dynamisches Laden von Assemblies und kein Erzeugen von Code zur Laufzeit. |

Quellen: [ReadyToRun deployment overview](https://learn.microsoft.com/dotnet/core/deploying/ready-to-run) („R2R binaries are larger because they contain both intermediate language (IL) code […] and the native version of the same code“), [Native AOT deployment overview](https://learn.microsoft.com/dotnet/core/deploying/native-aot/) („Native AOT apps don't use a just-in-time (JIT) compiler when the application runs“; Liste der Einschränkungen). *Stand: 2026-10-25.*

## Typische Fehlvorstellungen

:::warning[Achtung]
<Misconception id="m00-l05-compiles-to-machine-code" />

**„Der C#-Compiler erzeugt direkt Maschinencode.“** Standardmäßig erzeugt er IL. Maschinencode entsteht erst danach: zur Laufzeit durch den JIT, oder vorab bei ReadyToRun und Native AOT ([Managed Execution Process](https://learn.microsoft.com/dotnet/standard/managed-execution-process)).
:::

:::warning[Achtung]
<Misconception id="m00-l05-compile-error-at-runtime" />

**„Ein Compilerfehler zeigt sich erst, wenn die Zeile läuft.“** Der Compiler arbeitet vor dem Start und prüft den ganzen Quelltext. Mit einem Compilerfehler läuft keine Zeile, auch nicht die davor. Erst Laufzeitfehler treten mitten im Lauf auf, nachdem die Anweisungen davor gelaufen sind.
:::

## Kommst du aus …?

Die Vergleiche sind grobe Orientierung und nicht Teil der .NET-Dokumentation.

<FromLanguage>
<TabItem value="java">

Ähnliches Prinzip: Der Java-Compiler erzeugt Bytecode, den die JVM ausführt und dabei zur Laufzeit in Maschinencode übersetzt. IL entspricht dem Bytecode, die CLR der JVM.

</TabItem>
<TabItem value="python">

Python übersetzt Quelltext ebenfalls in Bytecode, den ein Interpreter ausführt. Ein Unterschied: Bei C# prüft der Compiler vor dem Start den ganzen Quelltext, etwa auf falsche Typen.

</TabItem>
<TabItem value="js">

JavaScript-Engines übersetzen Code oft erst zur Laufzeit mit einem JIT. Bei C# liegt vor dem JIT ein eigener Compilerschritt, der Fehler vor dem Start meldet.

</TabItem>
<TabItem value="go">

Go übersetzt Quelltext vorab in Maschinencode. Das entspricht in der Idee am ehesten Native AOT. Bei C# ist der JIT der Standard.

</TabItem>
</FromLanguage>

## Zusammenfassung

Der C#-Compiler übersetzt den Quelltext vor dem Start in IL. Der JIT der CLR macht daraus während des Laufs Maschinencode. Ein Compilerfehler verhindert den Start, ein Laufzeitfehler tritt auf, nachdem die Anweisungen davor gelaufen sind. ReadyToRun legt Maschinencode zusätzlich zur IL vorab ab und verkürzt so den Start. Native AOT übersetzt alles vorab, braucht keinen JIT, hat aber Einschränkungen.
