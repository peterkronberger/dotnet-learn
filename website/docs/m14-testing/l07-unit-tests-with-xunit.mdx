# Unit-Tests mit xUnit

:::note[Lernziele]
- Du kannst ein xUnit-Testprojekt anlegen und mit `dotnet test` ausführen.
- Du kannst einen Test nach dem Muster Arrange-Act-Assert schreiben und benennen.
- Du kannst eine passende `Assert`-Methode wählen (`Equal`, `True`/`False`, `Null`/`NotNull`, `Contains`, `Empty`).
- Du kannst die Ausgabe eines fehlschlagenden Tests lesen und die Ursache finden.

## Was ein Unit-Test ist

Bisher hast du ein Programm gestartet und die Ausgabe angesehen. Das prüft nur, was du gerade im Blick hast. Ein <Term id="unit-test">Unit-Test</Term> (unit test) prüft ein einzelnes Stück Code, zum Beispiel eine Methode oder eine Klasse. Er läuft in Millisekunden, braucht keine Datenbank und kein Netzwerk und meldet am Ende selbst, ob er bestanden hat oder fehlgeschlagen ist. Nach jeder Änderung führst du alle Tests aus und siehst sofort, ob etwas kaputtgegangen ist.

Zwei Bausteine laufen dabei zusammen. Ein <Term id="test-framework">Test-Framework</Term> (test framework) liefert die Attribute und Methoden, mit denen du Tests schreibst. In diesem Kurs ist das xUnit.net. NUnit, MSTest und TUnit erfüllen dieselbe Aufgabe und werden hier nur beim Namen genannt. Eine <Term id="test-platform">Testplattform</Term> (test platform) startet die Tests und spricht mit `dotnet test` und der IDE. Sie kommt weiter unten dran.

## Das Testprojekt

Tests liegen in einem eigenen Projekt, dem <Term id="test-project">Testprojekt</Term> (test project). Es verweist per Projektverweis (Lektion 2) auf den Code, den es testet. Das SDK legt es mit einer Vorlage an:

<Since dotnet="11" />

```bash
dotnet new xunit --xunit-version v3 -o tests/SecLog.Tests
dotnet reference add src/SecLog.Core --project tests/SecLog.Tests
dotnet sln add tests/SecLog.Tests
dotnet test
```

Die Option `--xunit-version v3` wählt xUnit v3. Die Vorlage legt außerdem die Datei `UnitTest1.cs` an. `dotnet reference add` und `dotnet sln add` kennst du aus Lektion 2. `dotnet test` baut das Testprojekt samt der Projekte, auf die es verweist, und führt die Tests aus.

So sieht die Projektdatei des Beispiels dieser Lektion aus:

## Ein Test mit Fact und Assert

Ein Test ist eine Methode mit dem Attribut `[Fact]` (Lektion 6). Das Attribut sagt xUnit: Diese Methode ist ein Test. Ein Fact hat keine Parameter und prüft eine Bedingung, die immer gelten soll. Die Prüfung selbst schreibst du mit einer <Term id="assertion">Assertion</Term> (assertion), also einem Aufruf von `Assert`. Trifft sie nicht zu, schlägt der Test fehl.

Die wichtigsten Methoden von `Assert`:

- `Assert.Equal(expected, actual)`: zwei Werte sind gleich. Der erwartete Wert steht zuerst.
- `Assert.True(condition)` und `Assert.False(condition)`: ein `bool` ist wahr oder falsch.
- `Assert.Null(value)` und `Assert.NotNull(value)`: ein Verweis ist `null` oder nicht.
- `Assert.Contains(item, collection)`: die Sammlung enthält das Element.
- `Assert.Empty(collection)`: die Sammlung ist leer.

Der Code unter Test ist eine kleine Regel für Passwörter. Eine Methode `IsValid` entscheidet, ob ein Passwort lang genug ist. `Problems` sammelt Meldungen, und `FirstProblem` liefert die erste oder `null`:

## Arrange-Act-Assert und Namen

Ein Test folgt einem festen Aufbau, <Term id="arrange-act-assert">Arrange-Act-Assert</Term>:

1. **Arrange:** Objekte anlegen und einrichten.
2. **Act:** genau eine Aktion ausführen, nämlich den Aufruf, den du testest.
3. **Assert:** das Ergebnis prüfen.

Der Name besteht aus drei Teilen: der getesteten Methode, dem Szenario und dem erwarteten Verhalten, zum Beispiel `IsValid_Null_ReturnsFalse`. Beim Fehlschlag weißt du dann ohne Code zu lesen, was nicht stimmt. Ein Test, der nur zwei Zeilen hat, braucht die Kommentare `// Arrange` und so weiter nicht. Der Aufbau bleibt trotzdem derselbe.

## Rot und grün

Ein Test muss fehlschlagen können. Du siehst das am besten, wenn du ihn einmal fehlschlagen lässt: erst rot (der Test schlägt fehl), dann den Code reparieren, dann grün (der Test besteht).

## Testplattform: VSTest und Microsoft.Testing.Platform

Die Testplattform startet die Tests. Es gibt zwei: VSTest ist die ältere. Die Microsoft.Testing.Platform (MTP) ist ein leichtgewichtiger Ersatz, der direkt im Testprojekt steckt. Bei xUnit v3 arbeitet `dotnet test` mit der MTP, wenn die Datei `global.json` das so einstellt. Die Vorlage des SDK legt das passend an. Mit `--test-runner VSTest` wählst du bei der Vorlage die ältere Plattform.

<Since dotnet="10" />

Die Vorlagen für xUnit v3 und NUnit mit der MTP als Standard gibt es seit dem .NET 11 SDK. Das Test-Framework bestimmt die Attribute und `Assert`-Methoden, die Plattform bestimmt, wie der Lauf abläuft. Beides ist getrennt austauschbar.

## Achtung

:::warning[Achtung]
<Misconception id="m14-l07-never-failing-test-is-good" />

**„Ein Test, der nie fehlschlägt, ist ein guter Test.“** Das stimmt nicht. Ein Test ist nur dann etwas wert, wenn er bei einem Fehler im Code rot wird. Die Vorlage des SDK legt zum Beispiel diesen Test an:

<CodeBlock language="csharp" title="UnitTest1.cs (Vorlage)">{templateTest}</CodeBlock>

`Assert.True(true)` prüft eine Konstante, keinen Code. Der Test ist immer grün und sagt nichts über dein Programm. Schreib einen Test so, dass du weißt, welche Änderung im Code ihn rot macht.
:::

Die Microsoft.Testing.Platform ist Open Source und steckt als Bibliothek im Testprojekt. Deshalb ist ein xUnit-v3-Testprojekt eine Executable. Neben xUnit.net unterstützen sie NUnit und MSTest. ## Zusammenfassung

Ein Unit-Test prüft ein kleines Stück Code und meldet selbst, ob er bestanden hat. Tests liegen in einem Testprojekt, das per Projektverweis auf den Code zeigt, und laufen mit `dotnet test`. Ein Test ist eine Methode mit `[Fact]`, geschrieben nach Arrange-Act-Assert und benannt nach Methode, Szenario und Erwartung. `Assert`-Methoden wie `Equal`, `True`, `Null`, `Contains` und `Empty` prüfen das Ergebnis. Die Meldung eines fehlgeschlagenen Tests nennt den erwarteten und den tatsächlichen Wert. Ein Test muss fehlschlagen können, sonst sagt er nichts aus.
