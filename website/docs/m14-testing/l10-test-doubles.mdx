## Warum Test-Doubles

In Lektion 9 hast du Eingaben als Parameter übergeben. Manchmal braucht Code aber etwas, das du nicht einfach als Zahl übergibst: das Versenden einer Nachricht, einen Netzwerkzugriff, eine Datei. Solche <Term id="dependency">Abhängigkeiten</Term> sind langsam, nicht immer verfügbar oder lösen etwas aus. Ein Unit-Test soll schnell und wiederholbar sein und nichts auslösen. Darum ersetzt du sie im Test durch ein <Term id="test-double">Test-Double</Term> (test double).

Der Austausch klappt, wenn der Code die Abhängigkeit über ein Interface (Modul 8) bekommt, nicht über eine feste Klasse. Das Double ist dann eine gewöhnliche Klasse, die dasselbe Interface implementiert.

## Stub, Spy, Fake

Die Begriffe sind nicht überall gleich belegt. Im üblichen .NET-Sprachgebrauch ist <Term id="fake">Fake</Term> der Oberbegriff. Ein <Term id="stub">Stub</Term> ist ein kontrollierbarer Ersatz, der feste Antworten liefert. Ein <Term id="mock">Mock</Term> ist ein Fake, gegen das der Test mit `Assert` prüft. Diese Lektion nutzt diese Begriffe und nennt zwei Klassen mit den Namen aus der Testliteratur:

- **Stub:** antwortet mit festen Werten. Damit erzeugst du Fälle auf Knopfdruck, etwa „Senden schlägt fehl“.
- **Spy:** zeichnet Aufrufe auf. Der Test prüft danach, ob und wie oft die Abhängigkeit aufgerufen wurde. Ein <Term id="spy">Spy</Term>, gegen den du mit `Assert` prüfst, ist in den Begriffen von Microsoft Learn ein Mock.
- **Fake (im engeren Sinn):** eine einfache, funktionierende Version des Originals, zum Beispiel im Speicher.

## Mocking-Bibliotheken und Augenmaß

Bibliotheken wie Moq, NSubstitute und FakeItEasy erzeugen Doubles zur Laufzeit, sodass du die Klassen nicht von Hand schreibst. Du brauchst sie nicht: Eine Klasse, die das Interface implementiert, genügt. Der Kurs nennt sie nur beim Namen.

Doubles sind ein Werkzeug mit Maß. Ersetze, was langsam, unzuverlässig oder mit Nebenwirkung ist. Nimm alles andere echt: Eine `List<string>` ersetzt du nicht. Wer zu viel ersetzt, testet am Ende die Doubles. Prüfe außerdem das Verhalten nach außen, etwa welche Nachricht rausgeht, und nicht, wie der Code intern arbeitet.

## Achtung

:::warning[Achtung]
<Misconception id="m14-l10-mocking-library-required" />

**„Um Code mit Abhängigkeiten zu testen, brauchst du eine Mocking-Bibliothek.“** Das stimmt nicht. Ein Double ist eine gewöhnliche Klasse, die das Interface implementiert. Du schreibst sie in wenigen Zeilen selbst. Eine Bibliothek spart nur Schreibarbeit, wenn es viele Doubles werden.
:::

<Quiz id="m14-l10-q6" />

<details>
<summary>Vertiefung: Begriffe in der Literatur (optional)</summary>

Die Begriffe Fake, Mock und Stub werden uneinheitlich benutzt. Im üblichen .NET-Gebrauch gilt: Fake ist ein Oberbegriff, ein Mock ist ein Fake, gegen den der Test prüft, ein Stub ein kontrollierbarer Ersatz. In der klassischen Literatur (Fowler, Meszaros) bedeutet Stub „liefert Daten“, Mock „prüft Interaktionen“ und Fake „funktionierende Ersatzimplementierung“ ([Unit testing terminology](https://learn.microsoft.com/dotnet/core/testing/unit-testing-best-practices#unit-testing-terminology)). Wichtig ist, dass du und dein Team dieselben Wörter für dieselben Dinge benutzen.

</details>

## Zusammenfassung

Ein Test-Double ersetzt im Test eine Abhängigkeit, die langsam, unzuverlässig oder mit Nebenwirkung ist. Der Code bekommt die Abhängigkeit über ein Interface, das Double implementiert es. Ein Stub liefert feste Antworten, ein Spy zeichnet Aufrufe auf, ein Fake ist eine einfache funktionierende Version. Mocking-Bibliotheken wie Moq, NSubstitute und FakeItEasy sind nicht nötig. Ersetze nur, was nötig ist, und prüfe das Verhalten nach außen.
