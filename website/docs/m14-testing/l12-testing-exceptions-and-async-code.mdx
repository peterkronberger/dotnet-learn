# Exceptions und asynchronen Code testen

:::note[Lernziele]
- Du kannst mit `Assert.Throws<T>` prüfen, dass eine Methode die richtige Exception wirft, und ihre Eigenschaften prüfen.
- Du kannst asynchrone Methoden mit `async Task`-Tests und `Assert.ThrowsAsync<T>` testen.
- Du kannst erklären, warum Testmethoden nicht `async void` sein dürfen.
:::

## Eine Exception als erwartetes Ergebnis

Manchmal ist die Exception das richtige Ergebnis: Eine Methode soll bei einem ungültigen Argument einen Fehler melden (Modul 7). Dann prüft der Test, dass sie geworfen wird. Das Muster der <Term id="exception-assertion">Exception-Prüfung</Term> ist `Assert.Throws<T>`. Du übergibst einen Lambda-Ausdruck (Modul 10) mit dem Aufruf. `Throws` führt ihn aus, erwartet genau den Typ `T` und gibt die Exception zurück. An ihr prüfst du die Eigenschaften, etwa `ParamName` oder `Message`.

`ThrowsAny<T>` nimmt dagegen `T` und alle abgeleiteten Typen. Der Unterschied zählt, wenn die Exception aus einer Vererbungskette kommt (Modul 7): `ArgumentNullException` erbt von `ArgumentException`.

## Asynchronen Code testen

Ein asynchroner Test ist eine Methode mit der Signatur `async Task` (Modul 13). Sie ruft die Methode mit `await` auf und prüft danach das Ergebnis. Ein <Term id="async-test">asynchroner Test</Term> gibt `Task` zurück, damit xUnit auf das Ende wartet. Für Exceptions in asynchronem Code gibt es `Assert.ThrowsAsync<T>` und `Assert.ThrowsAnyAsync<T>`. Beide musst du mit `await` abwarten.

Der Code unter Test zählt Fehlversuche mit einer kurzen Wartezeit je Zeile:

Die Methode bekommt ein `CancellationToken` (Modul 13). Im Test übergibst du `TestContext.Current.CancellationToken`: Das Token gehört zum laufenden Test, und xUnit löst es aus, wenn der Test abgebrochen wird, etwa durch ein Zeitlimit.

## Achtung

:::warning[Achtung]
<Misconception id="m14-l12-throws-accepts-derived-type" />

**„`Assert.Throws<ArgumentException>` besteht auch bei einer abgeleiteten Exception.“** Das stimmt nicht. `Throws<T>` verlangt genau den Typ `T`. Eine `ArgumentNullException` besteht `Throws<ArgumentException>` nicht. Willst du auch abgeleitete Typen zulassen, nimmst du `ThrowsAny<T>`.
:::

:::warning[Achtung]
<Misconception id="m14-l12-async-void-test-is-ok" />

**„Ein asynchroner Test darf `async void` sein.“** Das stimmt nicht. xUnit v3 unterstützt `async void` bei Tests nicht mehr. Ein Analyzer meldet das beim Bauen als Fehler. Ein Test gibt `Task` zurück, damit xUnit auf das Ende wartet.
:::

<details>
<summary>Vertiefung: Warum async void nicht geht (optional)</summary>

Eine Methode mit `async void` gibt dem Aufrufer nichts zurück, worauf er warten könnte (Modul 13). xUnit v3 bricht Tests mit dieser Signatur darum ab. Die Umstellung auf `Task` oder `ValueTask` ist Teil der Migration von v2 auf v3 ([Migration zu v3](https://xunit.net/docs/getting-started/v3/migration)). Der zugehörige Analyzer heißt xUnit1049 ([Analyzer-Regel](https://xunit.net/xunit.analyzers/rules/xUnit1049)).

</details>

## Zusammenfassung

`Assert.Throws<T>` prüft, dass ein Aufruf genau die Exception `T` wirft, und gibt sie zurück, damit du `ParamName`, `Message`, `LineNumber` und `InnerException` prüfst. `ThrowsAny<T>` akzeptiert auch abgeleitete Typen. Asynchrone Tests haben die Signatur `async Task`, rufen mit `await` auf und prüfen danach. Für Exceptions in asynchronem Code nimmst du `ThrowsAsync` oder `ThrowsAnyAsync` und wartest sie ab. Ein abgebrochenes `Task.Delay` wirft eine `TaskCanceledException`, darum passt dort `ThrowsAnyAsync<OperationCanceledException>`. `async void` ist bei xUnit v3 nicht erlaubt.
