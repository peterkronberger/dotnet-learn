## Wann Code schwer zu testen ist

Ein Test ruft Code auf und prüft das Ergebnis. Das klappt gut, wenn der Code ein Ergebnis zurückgibt und seine Eingaben als Parameter bekommt. Es klappt schlecht, wenn

- das Ergebnis nur auf der Konsole oder in einer Datei landet,
- der Code seine Eingaben selbst holt, etwa mit `Console.ReadLine()` oder aus einer Datei,
- der Code veränderlichen statischen Zustand benutzt (Modul 13, Lektion 15).

Code, bei dem das nicht zutrifft, heißt <Term id="testable-code">testbarer Code</Term> (testable code). Du erkennst ihn an einer Eigenschaft: Ein Test braucht einen Aufruf und eine Prüfung.

:::info[Vorhersage]
Das Programm meldet drei fehlgeschlagene Logins nacheinander. Wann erscheint die Zeile mit `ALARM`, und wie würdest du `Record` mit einem Test prüfen?
:::

1. **Zustand erkennen:** `failures` ist ein statisches Feld. Es behält seinen Wert zwischen den Aufrufen.
2. **Ablauf verfolgen:** Die ersten beiden Aufrufe erhöhen es auf 2, der dritte auf 3. Erst dann gilt `failures >= 3`, und die Zeile erscheint genau einmal.
3. **Prüfung suchen:** `Record` gibt nichts zurück. Das Ergebnis steht nur auf der Konsole, die ein Test schlecht abfragt.
4. **Folge:** Der Wert von `failures` hängt davon ab, wie oft vorher irgendein Test `Record` aufgerufen hat. Ein Test hängt dadurch von anderen ab.

Was passiert, wenn ein zweiter Test `Record` einmal aufruft? Er sieht den Zähler des ersten Tests und kann schon beim ersten Aufruf `ALARM` melden.

</details>

## Logik und Ein-/Ausgabe trennen

Die Lösung: Das Ergebnis kommt als Rückgabewert, die Eingaben kommen als Parameter. Eine Methode, deren Ergebnis nur von ihren Parametern abhängt und die sonst nichts verändert, heißt <Term id="pure-method">reine Methode</Term> (pure method). Mit denselben Eingaben liefert sie immer dasselbe Ergebnis. Die Konsole oder die Datei bleibt außerhalb, am Rand des Programms.

## Testabdeckung

Die <Term id="code-coverage">Testabdeckung</Term> (code coverage) misst, wie viel vom Code beim Testlauf ausgeführt wurde: Zeilen, Zweige oder Methoden. Hat Code zwei Zweige und ein Test durchläuft nur einen, meldet die Zweigabdeckung 50 %. Werkzeuge dafür gibt es mehrere, zum Beispiel Coverlet und die Microsoft-Erweiterung `Microsoft.Testing.Extensions.CodeCoverage`. Mit der Microsoft.Testing.Platform schaltest du sie mit `dotnet test --coverage` ein, sobald das Paket im Testprojekt steht.

Die Zahl sagt aber nur, was lief. Sie sagt nicht, ob das Ergebnis stimmt. Das zeigt das Beispiel: Die Regel soll ab 3 Fehlversuchen `medium` melden.

## Achtung

:::warning[Achtung]
<Misconception id="m14-l09-full-coverage-no-bugs" />

**„100 % Testabdeckung heißt: keine Fehler.“** Das stimmt nicht. Die Abdeckung zählt, welcher Code lief, nicht, ob das Ergebnis richtig ist. Im Beispiel oben führt ein Test jede Zeile aus, und die Regel hat trotzdem einen Fehler. Eine niedrige Zahl zeigt dir Code, den kein Test berührt. Eine hohe Zahl beweist nichts.
:::

<details>
<summary>Vertiefung: Abdeckung als Ziel (optional)</summary>

Eine hohe Abdeckung wird oft mit hoher Codequalität verbunden. Die Zahl allein kann die Qualität aber nicht belegen, und ein sehr hohes Ziel kann sogar schaden: Der Aufwand für die letzten Prozent steht schnell in keinem Verhältnis zum Nutzen ([Code coverage and code quality](https://learn.microsoft.com/dotnet/core/testing/unit-testing-best-practices#code-coverage-and-code-quality)).

</details>

## Zusammenfassung

Code ist leicht zu testen, wenn seine Logik von Ein- und Ausgabe getrennt ist und seine Eingaben als Parameter ankommen. Eine reine Methode liefert zu denselben Eingaben immer dasselbe Ergebnis und braucht einen Aufruf und eine Prüfung. Konsole, Datei und veränderlicher statischer Zustand erschweren Tests. Ein Testprojekt erreicht nur `public` Typen anderer Projekte, deshalb zieht SecLog den Parser nach `SecLog.Core`. Die Testabdeckung zeigt, welcher Code lief, aber nicht, ob die Ergebnisse stimmen.
