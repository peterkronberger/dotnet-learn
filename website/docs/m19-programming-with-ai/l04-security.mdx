## Was eine Studie zu Sicherheit gemessen hat

Lektion 3 fragte, ob ein Vorschlag stimmt. Diese Lektion fragt, ob er sicher ist. Eine Nutzerstudie hat das mit Aufgaben untersucht, bei denen Fehler Sicherheitslücken erzeugen.

**Studienergebnis** ([Perry et al., 2023](https://doi.org/10.1145/3576915.3623157)):

- **Gruppe:** 47 Teilnehmer, davon 33 mit KI-Assistent und 14 ohne. Es waren überwiegend Studierende.
- **Aufgabe:** fünf Aufgaben mit Sicherheitsbezug, zum Beispiel Text verschlüsseln, eine Nachricht signieren, Dateizugriff auf einen Ordner beschränken, einen Wert in eine SQL-Datenbank schreiben und eine Zahl mit Kommas in Text umwandeln. Drei Aufgaben waren in Python, eine in JavaScript, eine in C.
- **Werkzeug und Zeit:** ein Assistent auf Basis des Modells codex-davinci-002, also eine ältere Modellgeneration. Die Studie wurde 2022 veröffentlicht, die Konferenzfassung erschien 2023.
- **Ergebnis:** Bei vier der fünf Aufgaben schrieb die Gruppe mit Assistent häufiger unsichere Lösungen. Bei der fünften Aufgabe war das Bild gemischt. Die Gruppe mit Assistent bewertete ihre Lösungen außerdem häufiger als sicher.
- **Vertrauen:** Teilnehmer mit sicheren Lösungen vertrauten dem Assistenten im Mittel weniger als Teilnehmer mit unsicheren. Wer die Anfragen sorgfältiger formulierte, hatte weniger Schwachstellen (Lektion 5).
- **Einschränkungen:** kleine Stichprobe, überwiegend Studierende, künstliche Umgebung mit Zeitlimit und ohne Folgen. Die Autoren sind an der Universität Stanford. In den geprüften Teilen der Studie ist kein Interessenkonflikt genannt.

Gesamtbild: In dieser Studie und mit diesem älteren Werkzeug gab es mit Assistent mehr unsichere Lösungen, und sie wurden häufiger für sicher gehalten. Für heutige Werkzeuge sagt das nichts aus. Die Studie zeigt aber ein Muster, das du kennen solltest: Ein Vorschlag, der überzeugt, ist nicht deshalb sicher.

## Vertrauen kalibrieren

**Bewährte Praxis (nicht durch Studien belegt):** Du prüfst jeden Vorschlag mit der Checkliste aus [Lektion „Code-Review mit einer Checkliste“](../m18-final-project/l01-review-checklist). Für Sicherheit sind diese Punkte wichtig:

- **Punkt 6, SQL Injection:** Wird Eingabe zu einem Teil des SQL-Textes? ([Raw SQL sicher verwenden](../m16-ef-core/l09-raw-sql-safely))
- **Punkt 7, Eingabevalidierung:** Wird jede Eingabe geprüft, bevor sie benutzt wird? ([Parameterbindung und Validierung](../m17-aspnetcore-minimal-apis/l05-binding-validation))
- **Punkt 2, Ausnahmebehandlung:** Landet der Text einer Exception in einer Antwort an den Nutzer?
- **Zugriffsprüfung:** Verlangt jeder Endpunkt eine angemeldete Person (`RequireAuthorization`, [Endpunkte prüfen](../m18-final-project/l06-endpoint-review))?

Dabei ist die Verpackung des Vorschlags kein Beleg. Ein Assistent formuliert eine unsichere Lösung genauso sicher wie eine gute.

1. **Was soll der Code tun?** Eine Meldung als möglichen Phishing-Versuch einstufen, mit einem Link und einem Signalwort. Das tut der Code für den Normalfall.
2. **Checkliste Punkt für Punkt:** Punkt 1 (null): `message` ist nicht als nullable gekennzeichnet, wird aber nicht geprüft. Punkt 7 (Eingabe): Der Konstruktor prüft die Wörter nicht. Das Feld `signalWords` zeigt auf dasselbe Array wie die Variable des Aufrufers.
3. **Fund benennen und begründen:** Erstens: Ein `null`-Text löst eine `NullReferenceException` aus, statt abgewiesen zu werden. Zweitens: Wer das Array später ändert, ändert die Regel des bereits erzeugten Objekts. Ein Programmteil kann so die Erkennung abschwächen, ohne dass es auffällt.
4. **Korrektur vergleichen:** Die Klasse aus Modul 18 prüft `null` mit `ArgumentNullException.ThrowIfNull`, weist leere Listen und leere Wörter ab und legt mit `[.. signalWords]` eine eigene Kopie an. Du siehst sie beim Vergleich unten.

## Achtung

:::warning[Achtung]
<Misconception id="m19-l04-ai-code-secure-by-default" />

**„Code von einer KI ist sicher, weil sie aus sehr viel Code gelernt hat.“** Das stimmt nicht. Die Menge der Trainingsdaten sagt nichts über die Sicherheit eines einzelnen Vorschlags. In der Studie gab es mit Assistent bei vier von fünf Aufgaben mehr unsichere Lösungen.
:::

:::warning[Achtung]
<Misconception id="m19-l04-confident-answer-is-secure" />

**„Wenn die KI ihre Lösung sicher und begründet präsentiert, ist sie auch sicher.“** Das stimmt nicht. Eine Begründung ist Text, und der Ton sagt nichts über den Code. Prüfe den Code mit der Checkliste, nicht die Sicherheit der Formulierung.
:::

## Zusammenfassung

In einer Studie mit 47 Teilnehmern schrieb die Gruppe mit einem Assistenten auf Basis eines älteren Modells bei vier von fünf Sicherheitsaufgaben häufiger unsichere Lösungen und hielt sie häufiger für sicher. Die Stichprobe war klein und überwiegend studentisch. Wer dem Assistenten weniger vertraute, hatte sicherere Lösungen. Als Praxis bietet sich an, jeden Vorschlag mit der Review-Checkliste zu prüfen: SQL Injection, Eingabevalidierung, Ausnahmebehandlung und Zugriffsprüfung. Das ist Bewährte Praxis und kein Studienergebnis.
