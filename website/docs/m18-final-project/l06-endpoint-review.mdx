## Ein Endpunkt im Review

Ein <Term id="endpoint">Endpunkt</Term> nimmt Eingaben von außen an. Darum sind die Web-Punkte der Checkliste aus Lektion 1 ([Code-Review mit einer Checkliste](./l01-review-checklist)) hier besonders wichtig:

- **Autorisierung:** Wer darf den Endpunkt aufrufen? Es fehlt `RequireAuthorization` ([Wer darf den Endpunkt aufrufen?](../m17-aspnetcore-minimal-apis/l11-authentication-authorization)).
- **Punkt 7, Eingabevalidierung:** Prüft die App die Eingabe, bevor der Handler läuft? ([Parameterbindung und Validierung](../m17-aspnetcore-minimal-apis/l05-binding-validation)).
- **Punkt 4, async:** Es gibt einen `CancellationToken`, und nichts blockiert mit `.Result` ([Services und Abbruch in Endpunkten](../m17-aspnetcore-minimal-apis/l09-di-cancellation), [Stolperfallen bei async](../m13-async-concurrency/l08-async-pitfalls)).
- **Fehlerantworten:** Die Antwort enthält keine Details der Exception, sondern <Term id="problem-details">Problem Details</Term> ([Fehler als Problem Details](../m17-aspnetcore-minimal-apis/l07-problem-details)).
- **Punkt 6, SQL Injection:** Kein Wert wird in den SQL-Text verkettet ([Raw SQL sicher verwenden](../m16-ef-core/l09-raw-sql-safely)).
- **Punkt 5, Lebensdauer:** Ein Service mit kurzer Lebensdauer wird nicht von einem Singleton festgehalten ([Lebensdauern richtig kombinieren](../m15-dependency-injection-hosting/l04-combining-lifetimes)).

Jeder Befund nennt die Stelle, das Risiko und den Vorschlag.

## Eine Regel für alle Endpunkte

Ein Review prüft den Code von heute. Ein neuer Endpunkt von morgen wird nicht mehr geprüft, wenn niemand hinsieht. Ein Test kann die Regel „jeder Endpunkt unter `/incidents` verlangt eine Anmeldung“ für alle Endpunkte festhalten.

Dazu fragt der Test die App nach ihren Endpunkten. Die <Term id="endpoint-data-source">EndpointDataSource</Term> kennt jeden Endpunkt als `RouteEndpoint` mit der Routenvorlage und den <Term id="endpoint-metadata">Metadaten</Term>. `RequireAuthorization()` legt an jeden Endpunkt eine Metadaten-Angabe `IAuthorizeData` ([EndpointDataSource](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.routing.endpointdatasource), [Routing in ASP.NET Core](https://learn.microsoft.com/aspnet/core/fundamentals/routing)). Fehlt sie, ist der Endpunkt offen.

## Projektschritt

**Stand bisher:** In SecLog (`_ci/seclog-m18-l05/`) steht die Gruppe `/incidents` mit `RequireAuthorization()`. Einzelne Tests prüfen den Zugriff ohne Anmeldung, aber keiner prüft alle Endpunkte.

**Neue Anforderung:** „Ein Test prüft alle Endpunkte unter `/incidents`: Jeder verlangt eine Anmeldung. Kommt später ein Endpunkt ohne `RequireAuthorization` dazu, schlägt der Test fehl.“ Schreibe `EndpointRulesTests` mit der `SecLogApiFactory`. Ein Web-Projekt läuft nicht im Playground, darum steht hier nur die Musterlösung.

<details>
<summary>Musterlösung anzeigen</summary>

<CodeBlock language="csharp" title="tests/SecLog.Api.Tests/EndpointRulesTests.cs (neu)">{rulesTests}</CodeBlock>

1. **App bauen:** `factory.CreateClient()` baut und startet die App im Testserver. Erst danach sind die Endpunkte samt Gruppenregeln in der `EndpointDataSource`. Darum steht der Aufruf vor der Abfrage.
2. **Endpunkte holen:** Die `EndpointDataSource` kommt aus `factory.Services`. `OfType<RouteEndpoint>()` behält die Endpunkte mit Routenvorlage, `Where` die unter `/incidents`.
3. **Nicht leer:** `Assert.NotEmpty` verhindert, dass der Test besteht, weil er nichts gefunden hat.
4. **Regel prüfen:** Jeder Endpunkt braucht Metadaten vom Typ `IAuthorizeData`. Die Meldung nennt die Route des fehlenden Endpunkts.
5. **Produktionscode:** Das Review fand in `src/SecLog.Api/` kein Problem. Es ändert sich nur der Test.
6. **Ausgabe:** Die Konsolenausgabe bleibt gleich. In `expected.out.txt` kommt nur eine Testzeile dazu.

</details>

**Neuer Stand:** In SecLog (`_ci/seclog-m18-l06/`) sichert ein Test ab, dass jeder Endpunkt unter `/incidents` eine Anmeldung verlangt. Damit hat SecLog den Endstand des Kursprojekts erreicht (Vision in `concept/project-seclog.md`).

### Rückblick auf SecLog

SecLog ist über den ganzen Kurs gewachsen: Es liest und prüft Logzeilen, zählt Fehlversuche, verwaltet Vorfälle, bewertet Meldungen, speichert in einer Datenbank, bietet eine API an und hat Tests für seine Regeln. Die Checkliste aus Lektion 1 hilft dir, solchen Code zu prüfen.

## Achtung

:::warning[Achtung]
<Misconception id="m18-l06-green-tests-secure-endpoint" />

**„Wenn alle Tests grün sind, hat ein Endpunkt keine Sicherheitsprobleme.“** Tests prüfen nur die Fälle, die jemand geschrieben hat. Ein Endpunkt ohne `RequireAuthorization` besteht jeden Test, der nicht nach der Anmeldung fragt. Darum gibt es das Review, und darum gibt es Regeltests wie `EndpointRulesTests`.
:::

:::warning[Achtung]
<Misconception id="m18-l06-one-finding-enough" />

**„Ein Review ist fertig, sobald man ein Problem gefunden hat.“** Der Endpunkt dieser Lektion hat sechs Probleme. Ein Review geht die ganze Checkliste durch.
:::

## Zusammenfassung

Ein Review eines Endpunkts prüft Autorisierung, Eingabevalidierung, `CancellationToken`, Fehlerantworten und SQL. Jeder Befund bekommt Stelle, Risiko und Lösung. Grüne Tests beweisen keine Sicherheit. Ein Test über die `EndpointDataSource` hält die Regel „jeder Endpunkt verlangt eine Anmeldung“ für alle Endpunkte fest, auch für künftige.
