## Das SQL lesen

Bei EF-Core-Code reicht das Lesen von C# nicht aus. Die Abfrage `db.Incidents.Where(…)` sagt nicht, was die Datenbank bekommt. Ein Review fragt deshalb zuerst: Welches SQL entsteht? Die Antwort zeigt, ob die Datenbank filtert, ob ein Wert als <Term id="sql-parameter">Parameter</Term> ankommt und wie viele Befehle gehen.

`ToQueryString()` zeigt das SQL einer Abfrage, ohne sie auszuführen (Lektion [Von LINQ zu SQL](../m16-ef-core/l04-linq-to-sql)). Es gehört zum Handwerkszeug des Reviews. Dazu kommt die Frage aus der Lektion [IQueryable und IEnumerable](../m16-ef-core/l05-iqueryable-vs-ienumerable): Was wird übersetzt, und was läuft im Speicher? Der Teil vor `AsEnumerable()` wird zu SQL, alles danach läuft in C#.

Die Datenbankpunkte der Checkliste aus Lektion 1 ([Code-Review mit einer Checkliste](./l01-review-checklist)) sind:

- **Punkt 4, async:** `ToList()` oder `.Result` in einer `async`-Methode und ein fehlender `CancellationToken` ([Stolperfallen bei async](../m13-async-concurrency/l08-async-pitfalls), [Asynchrone Abfragen und Kontext-Lebensdauer](../m16-ef-core/l10-async-and-context-lifetime)).
- **Punkt 5, Lebensdauer:** Ein `DbContext` in einem Singleton oder einem statischen Feld ([Lebensdauern richtig kombinieren](../m15-dependency-injection-hosting/l04-combining-lifetimes)).
- **Punkt 6, SQL Injection:** Wird ein Wert Teil des SQL-Textes ([Raw SQL sicher verwenden](../m16-ef-core/l09-raw-sql-safely))?
- **Zusätzlich:** Das <Term id="n-plus-one-problem">N+1-Problem</Term> ([Verwandte Daten laden](../m16-ef-core/l06-loading-related-data)).

1. **Übersetzte Abfrage:** `Where`, `OrderBy` und `Select` werden zu `WHERE`, `ORDER BY` und einer Spaltenliste. Der Wert der Variablen `user` geht als Parameter `@user` an die Datenbank, steht also nicht im SQL-Text.
2. **`FromSql` mit Interpolation:** Der eingesetzte Wert wird zum Parameter `@p0`. Die Schreibweise sieht nach Textverkettung aus, ist aber keine.
3. **`FromSqlRaw` mit Verkettung:** Das `+` läuft in C#, bevor `FromSqlRaw` den Text bekommt. `bob` steht im SQL-Text, und es gibt keinen Parameter ([SQL Queries](https://learn.microsoft.com/ef/core/querying/sql-queries)). Mit einem harmlosen Namen merkt man nichts. Das Problem zeigt sich erst, wenn ein Wert mit SQL-Zeichen kommt (Lektion [Raw SQL sicher verwenden](../m16-ef-core/l09-raw-sql-safely)).
4. **Filter nach `AsEnumerable()`:** Der Teil vor `AsEnumerable()` hat kein `WHERE`. Die Datenbank liefert alle Zeilen, und C# filtert danach.

**Was passiert, wenn …?** … die Tabelle eine Million Vorfälle hat? Bei Abfrage 1 kommen nur die Zeilen von `bob` an. Bei Abfrage 4 kommen alle Zeilen an, und C# wirft die meisten weg.

</details>

## Befunde aus der Checkliste

Die vier Befunde stehen als Beispiele nebeneinander:

1. **SQL Injection (Punkt 6):** `FromSqlRaw` mit `+` oder mit interpolierten Werten macht eine Eingabe zum Teil des Befehls. `FromSql` mit Interpolation sendet jeden Wert als Parameter. Die Warnung EF1003 des Compilers meldet verkettetes `FromSqlRaw`. Nimm sie ernst, auch wenn der Name harmlos ist.
2. **Blockieren statt `await` (Punkt 4):** `ToList()` in einer `async`-Methode hält den Thread, bis die Datenbank antwortet. `ToListAsync(cancellationToken)` gibt ihn frei und bricht mit der Anfrage ab.
3. **Lebensdauer des Contexts (Punkt 5):** Ein `DbContext` ist für eine Unit of Work gedacht. Ein statisches Feld oder ein Singleton teilt ihn mit allen Aufrufen, und er ist nicht für parallele Zugriffe gebaut ([DbContext Lifetime](https://learn.microsoft.com/ef/core/dbcontext-configuration/)).
4. **N+1:** Eine Schleife, die pro Zeile eine Abfrage stellt, sendet 1 + N Befehle. `Include` oder eine Projektion lädt dasselbe mit einem Befehl ([Efficient Querying](https://learn.microsoft.com/ef/core/performance/efficient-querying)).

## Achtung

:::warning[Achtung]
<Misconception id="m18-l05-same-result-same-sql" />

**„Zwei Abfragen mit gleichem Ergebnis schicken dasselbe SQL an die Datenbank.“** Das Ergebnis sagt nichts über den Weg. Mit `AsEnumerable()` vor dem `Where` lädt die Datenbank alle Zeilen, und C# filtert. Das Ergebnis ist dasselbe, der Aufwand nicht. Ein Review liest deshalb das SQL.
:::

<details>
<summary>Vertiefung: Was `ToQueryString()` nicht zeigt (optional)</summary>

`ToQueryString()` zeigt das SQL einer einzelnen Abfrage, ohne sie auszuführen. Es zeigt nicht, wie oft eine Abfrage läuft: Ein N+1 in einer Schleife fällt erst auf, wenn man die Befehle zählt, wie in Lektion [Verwandte Daten laden](../m16-ef-core/l06-loading-related-data). Das protokollierte SQL aus dem Logging zeigt dagegen auch die Befehle, die wirklich laufen ([Simple Logging](https://learn.microsoft.com/ef/core/logging-events-diagnostics/simple-logging)).

</details>

## Zusammenfassung

Ein Review von EF-Core-Code liest das SQL: Mit `ToQueryString()` sieht man, ob die Datenbank filtert, ob ein Wert als Parameter ankommt und was nach `AsEnumerable()` im Speicher läuft. Aus der Checkliste gehören vier Befunde dazu: verkettetes `FromSqlRaw`, blockierende Aufrufe ohne Token in `async`-Methoden, ein geteilter `DbContext` und N+1. Ein Test sichert die Form des SQL ab. In SecLog ist das die Methode `Search` mit zwei Tests.
