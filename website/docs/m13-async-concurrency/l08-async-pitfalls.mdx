# Stolperfallen bei async

:::note[Lernziele]
- Du kannst erklären, warum `async void` nur für Event-Handler gedacht ist, und eine `async void`-Methode in eine `async Task`-Methode umschreiben.
- Du kannst erklären, warum man nicht mit `.Result` oder `.Wait()` auf einen Task wartet.
- Du kannst entscheiden, ob Arbeit I/O-gebunden oder CPU-gebunden ist, und was das für `async` bedeutet.
- Du kannst einen asynchronen Event-Handler sicher schreiben.
:::

## Eine Methode, die man nicht abwarten kann

Der Compiler hält jede Methode mit `async` für gültig, auch wenn ihr Rückgabetyp `void` ist. Das Beispiel ruft eine solche Methode auf:

:::info[Vorhersage]
Welche Zeilen erscheinen, und in welcher Reihenfolge?
:::

<details>
<summary>Lösung und Erklärung anzeigen</summary>

1. **Start:** Das Programm gibt `Start` aus und ruft `SendAlert` auf.
2. **Bis zum ersten await:** Die Methode läuft synchron weiter, gibt `Sending alert for bob` aus und trifft auf `await Task.Delay(10)`. Der Task ist nicht fertig, die Methode gibt die Kontrolle zurück.
3. **Der Aufrufer läuft weiter:** Weil `SendAlert` keinen Task zurückgibt, kann der Aufrufer nicht darauf warten. Er gibt `After the call` aus, und das Programm endet.
4. **Die letzte Zeile fehlt:** `Alert for bob sent` käme erst nach dem Warten. Zu dem Zeitpunkt ist das Programm schon zu Ende.

Das Ergebnis eines echten Laufs: `Start`, `Sending alert for bob`, `After the call`. Die vierte Zeile erscheint nie.

</details>

Eine <Term id="async-void">`async void`-Methode</Term> gibt keinen Task zurück. Der Aufrufer kann deshalb nicht auf sie warten. Ihre Ausnahmen kann er auch nicht abfangen: Sie werden nicht am Aufrufer ausgelöst, und eine unbehandelte Ausnahme kann das Programm beenden ([Async return types](https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/async-return-types)).

<CodeBlock language="csharp" title="async-void-exception.cs">{asyncVoidException}</CodeBlock>

Der `catch` in diesem Programm fängt die Ausnahme nicht. Der Aufruf kehrt zurück, bevor die Ausnahme auftritt. `Caught` erscheint nie.

## async Task statt async void

Die Lösung ist `async Task`. Der Task steht für die Arbeit, der Aufrufer wartet mit `await` darauf. Eine Ausnahme der Methode steckt im Task und wird am `await` ausgelöst.

:::info[Vorhersage]
Das Programm ruft dieselbe Methode zweimal auf, beide Male mit `await`. Welche Zeilen erscheinen?
:::

<CSharpRunner id="m13-l08-fix" code={asyncTaskFix} predict expected={asyncTaskFixOutput} />

<details>
<summary>Lösung und Erklärung anzeigen</summary>

1. **Erster Aufruf:** `SendAlertAsync("bob")` gibt `Sending alert for bob` aus, wartet und gibt `Alert for bob sent` aus. Erst dann läuft der Aufrufer weiter und gibt `After the call` aus.
2. **Zweiter Aufruf:** Die Methode löst eine `ArgumentException` aus. Sie steckt im Task und wird am `await` ausgelöst, der `catch` fängt sie.

</details>

## Ausnahme: Event-Handler

Es gibt einen Fall, in dem `async void` richtig ist. Der Delegate `EventHandler` hat den Rückgabetyp `void`. Eine Methode oder Lambda, die ein Ereignis abonniert, muss deshalb `void` zurückgeben. Soll sie `await` benutzen, ist `async void` die einzige Möglichkeit. In Modul 10 war das als offene Frage markiert: asynchrone Event-Handler.

Wenn du einen solchen Handler schreibst, fange alle Ausnahmen darin ab. Niemand außer dem Handler kann es tun.

<CodeBlock language="csharp" title="safe-async-handler.cs">{safeAsyncHandler}</CodeBlock>

Es geht auch ohne `async void`. Der Handler ist eine normale Lambda: Sie startet die `async Task`-Methode und speichert den Task. Das Programm wartet später auf alle gespeicherten Tasks. So gehen weder Ausnahmen noch laufende Arbeit verloren.

<CSharpRunner id="m13-l08-handler" code={handlerWithTasks} />

Beide Handler haben schon zurückgegeben, bevor die Tasks fertig sind. `Task.WhenAll` wartet auf beide. Ein Task, der eine Ausnahme enthält, löst sie dort aus, wo das Programm darauf wartet.

## Nicht blockieren, sondern warten

Ein Task lässt sich auch blockierend abwarten: mit `.Result`, `.Wait()` oder `GetAwaiter().GetResult()`. Der aufrufende Thread tut dann nichts, bis der Task fertig ist. Er ist belegt, obwohl er nur wartet. Das <Term id="sync-over-async">blockierende Warten auf einen Task</Term> ist deshalb ein typischer Fehler ([Asynchronous programming scenarios](https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/async-scenarios)).

<CodeBlock language="csharp" title="blocking-on-task.cs">{blockingOnTask}</CodeBlock>

Dazu kommt ein Risiko. In manchen Anwendungen gibt es einen <Term id="synchronization-context">Synchronisationskontext</Term>: Er sorgt dafür, dass die Fortsetzung nach einem `await` auf einem bestimmten Thread läuft, etwa dem der Oberfläche. Blockiert dieser Thread auf einen Task, dessen Fortsetzung genau auf ihm laufen soll, warten beide aufeinander. Das ist ein Deadlock. Eine Konsolenanwendung hat keinen solchen Kontext, dort verschwendest du nur einen Thread. Im Browser-Playground schlägt das blockierende Warten sofort fehl.

<Forward concepts={['Deadlock']} module="13" />

Schreibe stattdessen `await`. Es wartet, ohne den Thread zu blockieren.

<Quiz id="m13-l08-q6" />

## I/O-gebunden oder CPU-gebunden

Wie du asynchron arbeitest, hängt davon ab, worauf die Arbeit wartet. <Term id="io-bound">I/O-gebundene</Term> Arbeit wartet auf die Außenwelt: auf die Festplatte, das Netzwerk oder einen Timer. Dafür gibt es asynchrone Methoden, die du mit `await` abwartest. Es wird kein zusätzlicher Thread gebraucht. <Term id="cpu-bound">CPU-gebundene</Term> Arbeit rechnet: Der Prozessor ist die ganze Zeit beschäftigt. Sie wird mit `Task.Run` auf einen anderen Thread gelegt, damit der aufrufende Thread frei bleibt ([Asynchronous programming scenarios](https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/async-scenarios)).

## Achtung

:::warning[Achtung]
<Misconception id="m13-l08-async-void-is-safe" />

**„`async void` ist für jede Methode ohne Rückgabewert in Ordnung.“** Das stimmt nicht. Eine `async void`-Methode kann nicht abgewartet werden, und der Aufrufer fängt ihre Ausnahmen nicht ab. Methoden ohne Ergebnis sind `async Task`. `async void` ist nur für Event-Handler gedacht.
:::

<Quiz id="m13-l08-q3" />

<details>
<summary>Vertiefung: Synchronisationskontext und async all the way (optional)</summary>

Ein `await` merkt sich den aktuellen Synchronisationskontext, wenn es einen gibt, und setzt die Methode dort fort. In Bibliothekscode ist das oft nicht nötig. Mit `ConfigureAwait(false)` verzichtet ein `await` darauf. Das kann Leistung bringen und hilft, Deadlocks zu vermeiden, wenn ein Aufrufer blockiert. In Anwendungscode mit Oberfläche lässt man es meistens weg. Hier ist `ConfigureAwait` nur genannt ([Asynchronous programming scenarios](https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/async-scenarios)).

<CodeBlock language="csharp" title="configure-await.cs">{configureAwait}</CodeBlock>

„Async all the way“ heißt: Wer eine asynchrone Methode aufruft, wartet mit `await` und ist selbst `async`. So zieht sich `async` bis zum Einstiegspunkt durch und nirgends muss blockiert werden. Blockiert werden darf nur, wenn `await` auf dem ganzen Aufrufweg nicht möglich ist, zum Beispiel in einer alten Schnittstelle, die du nicht ändern kannst.

</details>

## Zusammenfassung

`async void` gibt keinen Task zurück: Der Aufrufer kann nicht warten und keine Ausnahme abfangen. Es ist nur für Event-Handler gedacht, alle anderen Methoden ohne Ergebnis sind `async Task`. Ein sicherer Handler startet eine `async Task`-Methode und speichert den Task, das Programm wartet danach mit `Task.WhenAll`. `.Result`, `.Wait()` und `GetAwaiter().GetResult()` blockieren einen Thread und können mit einem Synchronisationskontext einen Deadlock auslösen, `await` wartet ohne Blockieren. I/O-gebundene Arbeit wartet man mit `await` auf die asynchrone API ab, CPU-gebundene Arbeit legt man mit `Task.Run` auf einen anderen Thread.
