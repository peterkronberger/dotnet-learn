# Ausnahmen in asynchronem Code

:::note[Lernziele]
- Du kannst vorhersagen, wann eine Ausnahme aus einer async-Methode beim Aufrufer ankommt (beim `await`, nicht beim Aufruf).
- Du kannst eine Ausnahme aus einer async-Methode mit `try`/`catch` um das `await` behandeln.
- Du kannst erklären, warum ein Task, auf den nie gewartet wird, seine Ausnahme „verschluckt“.
- Du kannst `IsFaulted` und `IsCompletedSuccessfully` eines Tasks deuten.
:::

## Wohin geht die Ausnahme?

Eine Ausnahme wandert normalerweise die Aufrufkette nach oben, bis eine passende `catch`-Klausel sie behandelt (<Term id="exception-propagation">Weitergabe</Term>). Bei `async` kehrt der Aufruf aber früh zurück, noch bevor der Rest der Methode läuft (Lektion „Wie eine async-Methode abläuft“). Wohin geht die Ausnahme dann?

Die Antwort: Die Methode gibt einen Task zurück, und die Ausnahme steckt in diesem Task. Der Task ist dann ein <Term id="faulted-task">fehlerhafter Task</Term> (Zustand „faulted“). Erst das `await` auf den Task löst die Ausnahme erneut aus, und zwar beim Aufrufer ([§15.14.3 Evaluation of a task-returning async function](https://learn.microsoft.com/dotnet/csharp/language-reference/language-specification/classes#15143-evaluation-of-a-task-returning-async-function)). Deshalb fängt ein `try`/`catch` um das `await` die Ausnahme ab.

:::info[Vorhersage]
Welche Zeilen gibt das Programm aus? Die Methode löst nach dem Warten eine `InvalidOperationException` aus.
:::

<CSharpRunner id="m13-l03-catch" code={catchAtAwait} predict expected={catchAtAwaitOutput} />

<details>
<summary>Lösung und Erklärung anzeigen</summary>

1. **Aufruf:** `ReadNumberAsync()` läuft bis zum `await Task.Delay(10)` und gibt einen unfertigen Task zurück. Die Zeilen 1 und 2 erscheinen, ohne dass etwas ausgelöst wird.
2. **Fehler im Task:** Nach dem Warten löst die Methode die Ausnahme aus. Sie wird im Task gespeichert, der Task ist fehlerhaft.
3. **Erneut ausgelöst:** Das `await pending` im `try`-Block löst die gespeicherte Ausnahme aus. Zeile 3 fehlt, weil der Code hinter dem `await` übersprungen wird. Die `catch`-Klausel gibt Zeile 4 aus.

Was passiert, wenn du `try` und `catch` nur um die Zeile `Task<int> pending = ReadNumberAsync();` setzt? Dann fängt es nichts, denn der Aufruf löst nichts aus. Das `await` steht außerhalb, und die Ausnahme wäre nicht behandelt.

</details>

Das `catch` fängt hier den Typ `InvalidOperationException`, nicht eine Sammelausnahme: Bei einem einzelnen Task löst `await` die ursprüngliche Ausnahme aus, nicht eine `AggregateException` (Sammelausnahme, mehr dazu in der nächsten Lektion).

## Auch ein früher Fehler steckt im Task

Der Fehler muss nicht nach einem `await` auftreten. Löst die Methode die Ausnahme aus, bevor sie auf einen unfertigen Task wartet, ist es genauso: Der Aufruf löst nichts aus, der zurückgegebene Task ist schon fehlerhaft. Mit `IsFaulted` fragst du ab, ob ein Task fehlerhaft ist.

## Was ein Task über sich verrät

Ein Task kennt seinen Zustand. Die beiden Eigenschaften, die du jetzt brauchst:

- `IsCompletedSuccessfully` ist `True`, wenn die Arbeit ohne Ausnahme fertig wurde.
- `IsFaulted` ist `True`, wenn die Arbeit mit einer Ausnahme endete.

Solange der Task noch läuft, sind beide `False`. Die Ausnahme selbst steht in der Eigenschaft `Exception` des Tasks (ein `AggregateException`-Objekt, dazu mehr in der nächsten Lektion). Wer sie liest, hat sie ebenfalls beachtet.

:::info[Vorhersage]
Zwei Tasks starten, einer gelingt, einer schlägt fehl. Auf den fehlerhaften wartet niemand. Welche drei Zeilen erscheinen? Läuft das Programm weiter?
:::

<CSharpRunner id="m13-l03-states" code={taskStates} predict expected={taskStatesOutput} />

<details>
<summary>Lösung und Erklärung anzeigen</summary>

1. **Zwei Tasks starten:** Beide laufen an und warten kurz. `await Task.Delay(100)` gibt ihnen genug Zeit, fertig zu werden.
2. **Zustände lesen:** `good` ist erfolgreich beendet, `IsCompletedSuccessfully` ist `True`. `lost` hat eine Ausnahme ausgelöst, `IsFaulted` ist `True`.
3. **Niemand wartet auf `lost`:** Kein `await` löst die Ausnahme aus, also erscheint keine Fehlermeldung, und das Programm läuft weiter. Die Ausnahme ist eine <Term id="unobserved-exception">unbeobachtete Ausnahme</Term>. Nach den Regeln von .NET wird sie erst behandelt, wenn der Task vom Garbage Collector eingesammelt wird ([Exception handling (Task Parallel Library)](https://learn.microsoft.com/dotnet/standard/parallel-programming/exception-handling-task-parallel-library)).

</details>

## Achtung

:::warning[Achtung]
<Misconception id="m13-l03-async-exception-lost" />

**„Eine Ausnahme in einer async-Methode geht verloren, weil die Methode schon zurückgekehrt ist.“** Das stimmt nicht, solange jemand auf den Task wartet: Die Ausnahme steckt im Task, und `await` löst sie erneut aus. Verloren geht sie nur, wenn niemand auf den Task wartet und niemand seine `Exception` liest. Dann läuft das Programm ohne Meldung weiter, wie bei `lost` im Programm oben.
:::

<details>
<summary>Vertiefung: Was bei mehreren Fehlern passiert (optional)</summary>

Ein Task kann mehrere Ausnahmen speichern, zum Beispiel wenn er auf mehrere andere Tasks wartet. Deshalb ist `Task.Exception` vom Typ `AggregateException`, das die einzelnen Ausnahmen in `InnerExceptions` sammelt. Beim `await` löst .NET trotzdem nur eine davon aus, nicht die Sammelausnahme ([Exception handling (Task Parallel Library)](https://learn.microsoft.com/dotnet/standard/parallel-programming/exception-handling-task-parallel-library)). Die nächste Lektion zeigt das mit `Task.WhenAll`.

</details>

## Zusammenfassung

Eine async-Methode, die einen Task zurückgibt, löst ihre Ausnahmen nicht beim Aufruf aus. Sie speichert sie im Task, der dann fehlerhaft ist (`IsFaulted`). Das `await` löst die Ausnahme erneut aus, deshalb gehört das `await` in den `try`-Block. Ohne `await` bleibt die Ausnahme im Task und geht unbemerkt verloren. Erfolgreiche Tasks erkennst du an `IsCompletedSuccessfully`.
