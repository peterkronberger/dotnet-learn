## Wer ruft auf, und darf er das?

Bisher darf jeder die API von SecLog aufrufen. Das ändert sich jetzt. Zwei Fragen sind dabei zu trennen:

- <Term id="authentication">Authentifizierung</Term>: **Wer** ruft auf?
- <Term id="authorization">Autorisierung</Term>: **Darf** dieser Aufrufer das tun?

Die erste Frage kommt zuerst, denn ohne bekannte Identität lässt sich über Rechte nichts sagen. Beide Schritte laufen in ASP.NET Core als Middleware (Lektion 8) vor dem Endpunkt ([Overview of ASP.NET Core Authentication](https://learn.microsoft.com/aspnet/core/security/authentication/)).

Das Ergebnis der Authentifizierung ist eine Identität. Sie besteht aus <Term id="claim">Claims</Term>: Angaben über den Benutzer als Name-Wert-Paare, zum Beispiel der Name oder die Rolle. Alle Claims einer Identität zusammen bilden den `ClaimsPrincipal`. Du erreichst ihn über `HttpContext.User` (Lektion 5 und 8).

### Woher kommt die Identität?

Ein <Term id="authentication-scheme">Authentifizierungsschema</Term> ist ein Name für einen Handler und seine Optionen. Der Handler liest die Zugangsdaten einer Anfrage und baut daraus die Identität. Bei einer API ist der übliche Fall ein <Term id="bearer-token">Bearer-Token</Term>: ein signiertes Token, das ein Client im Header `Authorization: Bearer …` mitsendet (Lektion 1 erklärt Header).

Die API stellt das Token nicht aus. Ein Identitätsanbieter verwaltet Benutzer und Passwörter und gibt die Tokens heraus. Die API prüft nur, ob Signatur, Aussteller und Zielgruppe des Tokens stimmen, und übernimmt dessen Claims. Wie ein Anbieter Tokens ausstellt (zum Beispiel mit OAuth 2.0 und OpenID Connect), ist ein eigenes Thema und gehört nicht zu diesem Kurs. Eigenen Sicherheitscode für Passwörter oder Signaturen schreibst du nicht.

In ASP.NET Core registrierst du das Schema für Bearer-Token so:

```csharp
builder.Services.AddAuthentication().AddJwtBearer();
```

`AddJwtBearer` steckt im Paket `Microsoft.AspNetCore.Authentication.JwtBearer`. Aussteller und Zielgruppe lesen Minimal APIs aus der Konfiguration, aus dem Abschnitt `Authentication:Schemes:Bearer` (Konfiguration: Modul 15). Es stehen keine Geheimnisse im Repository ([Authentication and authorization in Minimal APIs](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis/security)). Für lokale Tests erzeugt das Werkzeug `dotnet user-jwts` Tokens. Mehr als den Namen braucht dieser Kurs davon nicht.

### Die Regeln: Policies

Eine <Term id="authorization-policy">Policy</Term> ist ein benannter Satz von Anforderungen. `RequireRole("responder")` verlangt eine Rolle, `RequireClaim(…)` einen bestimmten Claim. Du registrierst die Policy einmal und hängst sie dann an Endpunkte:

- `AddAuthorizationBuilder().AddPolicy("Name", …)` legt die Policy an.
- `RequireAuthorization()` verlangt einen angemeldeten Benutzer, ohne weitere Regel.
- `RequireAuthorization("Name")` verlangt die benannte Policy.
- `AllowAnonymous()` nimmt einen Endpunkt von der Pflicht aus.

([Policy-based authorization in ASP.NET Core](https://learn.microsoft.com/aspnet/core/security/authorization/policies))

`RequireAuthorization` gibt es auch an einer Gruppe (Lektion 3). Dann gilt die Pflicht für alle Endpunkte der Gruppe.

:::note[Offen ist der Standard]
Die Einrichtung der Authentifizierung schützt keinen Endpunkt. Ein Endpunkt ohne jede Angabe zur Autorisierung ist für alle offen. Wer das umkehren will, setzt eine **Fallback-Policy**, die für jeden Endpunkt ohne Angabe gilt: `SetFallbackPolicy` mit einer Policy, die `RequireAuthenticatedUser()` verlangt. Dann ist Verweigern der Standard, und öffentliche Endpunkte markierst du mit `AllowAnonymous()`.
:::

### Reihenfolge der Middleware

`UseAuthentication()` setzt die Identität, `UseAuthorization()` prüft sie gegen die Regeln des Endpunkts. Die Authentifizierung muss zuerst laufen. `WebApplication` fügt beide Middleware selbst hinzu, sobald die zugehörigen Dienste registriert sind. Wer die Reihenfolge sichtbar halten oder steuern will, ruft sie ausdrücklich auf, so wie SecLog es unten tut ([Authentication and authorization in Minimal APIs](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis/security)).

### 401 und 403

Wenn die Regel nicht erfüllt ist, entscheidet die Lage über die Antwort:

- **`401 Unauthorized`:** Der Aufrufer ist nicht authentifiziert, es fehlt das Token oder es ist ungültig. Beim Bearer-Schema kommt dazu der Header `WWW-Authenticate: Bearer`.
- **`403 Forbidden`:** Der Aufrufer ist authentifiziert, hat aber nicht das Recht.

Die Namen führen in die Irre: `401` heißt „unauthorized“, meint aber die fehlende Authentifizierung ([Overview of ASP.NET Core Authentication](https://learn.microsoft.com/aspnet/core/security/authentication/)).

<details>
<summary>Vertiefung: Fallback-Policy und Standard-Policy (optional)</summary>

Für jeden Endpunkt wählt die Autorisierungs-Middleware die Policy aus seinen Angaben. Ohne Angabe gilt die Fallback-Policy, falls es eine gibt. `RequireAuthorization()` ohne Namen verwendet die Standard-Policy, die einen angemeldeten Benutzer verlangt. Eine benannte Policy ersetzt beide. Die Fallback-Policy wird nie mit einer benannten oder der Standard-Policy kombiniert ([Policy-based authorization: Default and fallback policies](https://learn.microsoft.com/aspnet/core/security/authorization/policies#default-and-fallback-policies)).

## Einen Benutzer im Test simulieren

Ein Integrationstest soll nicht bei einem Identitätsanbieter anfragen. Stattdessen ersetzt er das Schema durch einen eigenen Handler. Der Handler ist eine Klasse, die von `AuthenticationHandler<AuthenticationSchemeOptions>` erbt und eine Methode überschreibt, die die Identität baut. Der Test registriert ihn in `ConfigureTestServices` (Lektion 4) mit `AddAuthentication` und `AddScheme` ([Integration tests in ASP.NET Core: Mock authentication](https://learn.microsoft.com/aspnet/core/test/integration-tests#mock-authentication)).

Die Policy läuft dabei unverändert: Nur die Quelle der Identität wird ausgetauscht, die Regeln bleiben die der echten App. Darum testen solche Tests wirklich `401`, `403` und den Erfolg.

## Projektschritt

**Stand bisher:** SecLog (`_ci/seclog-m17-l10/`) bietet drei Endpunkte unter `/incidents` und ein OpenAPI-Dokument. Jeder darf alles aufrufen.

**Neue Anforderung:** „Nur angemeldete Benutzer dürfen Vorfälle lesen, und nur Benutzer mit der Rolle `responder` dürfen den Status ändern.“

Dafür kommt das Paket `Microsoft.AspNetCore.Authentication.JwtBearer` in `SecLog.Api.csproj`. In `Program.cs` stehen `AddAuthentication().AddJwtBearer()`, die Policy `ChangeIncidentStatus` mit `RequireRole("responder")` sowie `UseAuthentication()` und `UseAuthorization()` vor den Endpunkten. `appsettings.json` bekommt Aussteller und Zielgruppe, aber keinen Schlüssel und kein Geheimnis. Das OpenAPI-Dokument bleibt ohne Anmeldung erreichbar (`AllowAnonymous()`), bis Lektion 12 es auf die Entwicklung beschränkt. Die bisherigen Tests senden jetzt einen angemeldeten Benutzer, und die neuen Tests in `AuthorizationTests` prüfen `401`, `403` und `204`.

## Achtung

:::warning[Achtung]
<Misconception id="m17-l11-authentication-equals-authorization" />

**„Wer angemeldet ist, darf alle Endpunkte aufrufen.“** Die Anmeldung beweist nur, wer aufruft. Was die Identität darf, entscheiden Policies und Rollen an den Endpunkten. Ein angemeldeter Benutzer ohne die Rolle `responder` bekommt bei `PUT /incidents/1/status` ein `403`.
:::

:::warning[Achtung]
<Misconception id="m17-l11-401-and-403-same" />

**„`401` und `403` bedeuten dasselbe.“** `401` heißt: nicht authentifiziert, die Identität fehlt oder ist ungültig. `403` heißt: authentifiziert, aber nicht erlaubt. Ein Client kann mit einem neuen Token auf `401` reagieren. Auf `403` hilft ein neues Token mit demselben Benutzer nicht.
:::

<details>
<summary>Vertiefung: Claims und Rollen (optional)</summary>

Eine Rolle ist ein Claim vom Typ `ClaimTypes.Role`. `RequireRole("responder")` prüft, ob die Identität einen solchen Claim mit diesem Wert hat. Andere Regeln prüfen andere Claims, zum Beispiel mit `RequireClaim("scope", "incidents.write")`. Hinter einer Policy stehen Anforderungen und Handler, die den `ClaimsPrincipal` auswerten. Mehrere Anforderungen einer Policy müssen alle erfüllt sein ([Policy-based authorization](https://learn.microsoft.com/aspnet/core/security/authorization/policies)).

</details>

## Zusammenfassung

Authentifizierung stellt fest, wer aufruft, und liefert einen `ClaimsPrincipal`. Autorisierung entscheidet, ob diese Identität den Endpunkt aufrufen darf. Bei einer API liest ein Schema das Bearer-Token und prüft es, das Token stellt ein Identitätsanbieter aus. Endpunkte oder Gruppen verlangen mit `RequireAuthorization` eine Anmeldung oder eine benannte Policy, ohne Angabe sind sie offen, solange keine Fallback-Policy gilt. Fehlende Anmeldung ergibt `401`, fehlendes Recht `403`. Im Test ersetzt ein Test-Handler das Schema, und die Policy läuft wie in der echten App.
