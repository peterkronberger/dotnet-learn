# Statuscodes und typisierte Ergebnisse

:::note[Lernziele]
- Du wählst für einen Endpoint den passenden Statuscode: 200, 201 mit `Location`, 204, 400 oder 404.
- Du schreibst einen Handler mit `TypedResults` und dem Rückgabetyp `Results<Ok<T>, NotFound>`.
- Du erklärst, warum `null` als Rückgabe kein „nicht gefunden“ ist.
:::

## Der Handler wählt den Statuscode

Bisher hat die App den Statuscode selbst gewählt: 200 für jeden Rückgabewert und 404, wenn keine Route passt. Lektion 3 hat gezeigt, dass ein Handler, der für eine unbekannte Id `null` zurückgibt, mit `200 OK` und dem Body `null` antwortet. Für einen Client ist das schlecht: Er muss den Body lesen, um zu merken, dass es den Vorfall nicht gibt.

Eine Antwort hat einen Statuscode (Lektion 1), und den kann nur der Handler wählen, denn nur er weiß, was passiert ist. Dazu gibt er kein Objekt zurück, sondern ein **Ergebnis**: ein Objekt, das die ganze Antwort beschreibt. Die Schnittstelle dafür heißt `IResult`. Die Klasse `TypedResults` hat für jeden häufigen Fall eine Methode:

| Aufruf | Statuscode | Wann |
| --- | --- | --- |
| `TypedResults.Ok(value)` | 200 | Erfolg mit Body |
| `TypedResults.Created(uri, value)` | 201 | Eine neue Ressource entstand |
| `TypedResults.NoContent()` | 204 | Erfolg ohne Body, zum Beispiel nach `PUT` und `DELETE` |
| `TypedResults.BadRequest()` | 400 | Die Anfrage ist fehlerhaft |
| `TypedResults.NotFound()` | 404 | Die Ressource gibt es nicht |

Die Bedeutung der Codes legt RFC 9110 fest. `201 Created` sagt zusätzlich, wo die neue Ressource liegt: im <Term id="location-header">Location-Header</Term> der Antwort. `TypedResults.Created(uri, value)` setzt ihn aus dem ersten Argument. `400` kennst du schon von Bindung und Validierung. Die Antwort mit dem genauen Fehlerformat kommt in Lektion 7.

Es gibt auch die Klasse `Results` mit denselben Methoden, zum Beispiel `Results.NotFound()`. Ihr Rückgabetyp ist nur `IResult`. `TypedResults.NotFound()` liefert dagegen den Typ `NotFound`, ein <Term id="typed-result">typisiertes Ergebnis</Term>. Die Antwort ist dieselbe, der Unterschied liegt im Typ, und der hilft in zwei Fällen:

1. **Test:** Ein Test kann den Typ prüfen, ohne einen Server zu starten.
2. **Beschreibung:** Werkzeuge lesen aus dem Typ, welche Antworten ein Endpoint hat. Lektion 10 nutzt das für OpenAPI.

Hat ein Handler mehrere mögliche Ergebnisse, nennt der Rückgabetyp alle: `Results<Ok<IncidentDto>, NotFound>`. Das ist ein generischer Typ (Modul 9) mit zwei Typargumenten. Er sagt: Der Handler gibt entweder ein `Ok<IncidentDto>` oder ein `NotFound` zurück. Eine andere Rückgabe, etwa `TypedResults.BadRequest()`, übersetzt der Compiler nicht. Der Typ gehört zur Signatur, und der Compiler prüft ihn. Die Typen `Ok<T>`, `NotFound`, `NoContent` und `Created<T>` stehen im Namensraum `Microsoft.AspNetCore.Http.HttpResults`.

Das Programm hat vier Endpoints:

- `/null/{id}` gibt `FirstOrDefault` direkt zurück.
- `GET /incidents/{id}` gibt `Results<Ok<IncidentDto>, NotFound>` zurück.
- `POST /incidents` legt einen Vorfall an und gibt `Created` zurück.
- `DELETE /incidents/{id}` gibt `Results<NoContent, NotFound>` zurück.

Am Ende ruft das Programm `GetIncident(99)` ohne Server auf, denn ein Handler ist eine normale Methode. Das Ergebnis hat die Eigenschaft `Result`, die das tatsächlich gewählte Ergebnis enthält.

1. **`null`:** Der Handler gibt `null` zurück, ASP.NET Core schreibt `null` als JSON. Statuscode 200 mit dem Body `null`: Der Statuscode hängt nicht vom Wert ab.
2. **`Ok` oder `NotFound`:** Für Id 1 gibt der Handler `TypedResults.Ok(incident)` zurück: 200 mit dem Vorfall. Für Id 99 gibt er `TypedResults.NotFound()` zurück: 404 ohne Body.
3. **`Created`:** Die Antwort hat 201, den Header `Location: /incidents/3` und den neuen Vorfall im Body.
4. **`NoContent` oder `NotFound`:** Das erste `DELETE` löscht den Vorfall und antwortet mit 204 ohne Body. Das zweite findet ihn nicht mehr: 404.
5. **Ohne Server:** `GetIncident(99)` liefert ein `Results<…>`, dessen `Result` ein `NotFound` ist. Ein Test könnte genau das prüfen.

**Was passiert, wenn …** `GetIncident` zusätzlich `TypedResults.BadRequest()` zurückgibt, der Rückgabetyp aber unverändert bleibt? Der Compiler lehnt das ab, weil `BadRequest` im Typ fehlt.

## Achtung

:::warning[Achtung]
<Misconception id="m17-l06-null-means-not-found" />

**„Gibt ein Handler `null` zurück, antwortet die API automatisch mit 404.“** Die Antwort ist `200 OK` mit dem Body `null`. Wer 404 will, gibt `TypedResults.NotFound()` zurück.
:::

:::warning[Achtung]
<Misconception id="m17-l06-200-for-everything" />

**„Jeder erfolgreiche Aufruf antwortet mit 200.“** 200 meldet nur Erfolg. Ein neuer Vorfall verdient 201 mit `Location`, eine Änderung ohne Antwort-Body 204. Der Client erkennt am Code, was passiert ist.
:::

<details>
<summary>Vertiefung: Ergebnisse ohne Server testen (optional)</summary>

Ein Handler, der `TypedResults` zurückgibt, lässt sich als Methode aufrufen. Der Test prüft dann den Typ des Ergebnisses, ohne Server und ohne HTTP. Das Vorgehen steht im Abschnitt zu Unit-Tests von [Test Minimal API apps](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis/test-minimal-api). Dass `Results<T1, T2>` ein Ergebnis der Typen `T1` oder `T2` hält und die Eigenschaft `Result` den tatsächlichen Wert liefert, zeigt das Programm oben. Die Bedeutung der Statuscodes steht in [RFC 9110, Abschnitt 15](https://www.rfc-editor.org/rfc/rfc9110#name-status-codes).

</details>

## Zusammenfassung

Der Statuscode hängt nicht vom Wert ab, den ein Handler zurückgibt: Bei `null` antwortet die App mit 200 und dem Body `null`. Der Handler wählt den Code mit `TypedResults`: `Ok` für 200, `Created` für 201 mit `Location`, `NoContent` für 204, `BadRequest` für 400 und `NotFound` für 404. Der Rückgabetyp `Results<T1, T2>` nennt alle möglichen Ergebnisse, und der Compiler prüft ihn. Dadurch lässt sich ein Handler ohne Server testen, und Werkzeuge kennen die Antworten.
