:::note[Lernziele]

## Eine Anfrage ist ein Scope

In Modul 15 hast du gelernt, dass ein Scoped-Service in jedem DI-Scope einmal entsteht. Damals blieb offen, was in einer Web-App ein Scope ist. Die Antwort: Das Framework legt für jede Anfrage einen eigenen <Term id="request-scope">Scope</Term> an und gibt ihn frei, wenn die Antwort fertig ist ([Dependency injection in ASP.NET Core](https://learn.microsoft.com/aspnet/core/fundamentals/dependency-injection)). Ein Scoped-Service lebt darum genau eine Anfrage lang. Middleware und Handler derselben Anfrage teilen sich seine Instanz, die nächste Anfrage bekommt eine neue.

Genauso funktioniert der `DbContext`: `AddDbContext` registriert ihn als Scoped-Service (Lektion 10 in Modul 16). Jede Anfrage hat deshalb ihren eigenen Context, und parallele Anfragen teilen sich keinen.

Services registrierst du auf `builder.Services`, wie in Modul 15. Ein Handler bekommt sie als Parameter: Ist der Typ des Parameters registriert, füllt das Framework ihn aus dem Container, ohne Attribut. Das zeigt das Programm unten. Es registriert zwei Services:

- `RequestCounter` ist Scoped. Jede neue Instanz bekommt die nächste Nummer.
- `AppCounter` ist ein Singleton und zählt alle Anfragen. Viele Anfragen laufen gleichzeitig und benutzen dieselbe Instanz, darum zählt er mit `Interlocked` (Modul 13) und nicht mit `++` (Strategien für Thread-Sicherheit, Lektion 15 in Modul 13).

Die Middleware holt ihren `RequestCounter` über `context.RequestServices`. Das ist der Service-Provider des Anfrage-Scopes. Du nutzt ihn hier nur, um zu zeigen, dass auch die Middleware im selben Scope läuft. Im eigenen Code fragst du einen Service lieber als Parameter an, statt ihn mit `GetRequiredService` zu holen: Dieses Muster heißt Service Locator und versteckt die Abhängigkeiten einer Klasse. Die Dokumentation rät davon ab.

## Wie ein Handler an Services kommt

Für den Parameter eines Handlers gibt es drei Schreibweisen ([Parameter binding in Minimal API apps](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis/parameter-binding)):

- **Ohne Attribut:** `(IIncidentService incidents) => …`. Das Framework erkennt, dass der Typ registriert ist.
- **Mit `[FromServices]`:** Dasselbe, aber ausdrücklich. Es ist nur nötig, wenn das Framework sonst raten müsste.
- **Mit `[FromKeyedServices("name")]`:** <Since dotnet="8" /> Der Parameter holt den Service, der mit `AddKeyedScoped` (oder `AddKeyedSingleton`, `AddKeyedTransient`) unter diesem Schlüssel registriert ist. Keyed Services kennst du aus Modul 15.

Ein Singleton darf keinen Scoped-Service im Konstruktor halten, sonst entsteht die Captive Dependency aus Modul 15: Er würde die erste Instanz für immer festhalten. Ein Handler hat dieses Problem nicht, denn er läuft innerhalb des Anfrage-Scopes.

## Abbruch: der CancellationToken der Anfrage

Ein Client kann eine Anfrage aufgeben: Der Benutzer schließt den Tab, oder eine Zeitgrenze läuft ab. Der Server merkt das und bricht den <Term id="cancellation-token">`CancellationToken`</Term> der Anfrage ab (Modul 13). Du bekommst ihn, indem du im Handler einen Parameter vom Typ `CancellationToken` anlegst. Das Framework bindet ihn an <Term id="request-aborted">`HttpContext.RequestAborted`</Term>.

Der Abbruch ist kooperativ, wie in Modul 13: Das Framework setzt nur den Token. Eine Datenbankabfrage stoppt nur, wenn du ihn an `ToListAsync`, `FirstOrDefaultAsync` oder `SaveChangesAsync` weitergibst. Dann wirft der Aufruf eine `OperationCanceledException`, und die Arbeit endet. Eine Antwort bekommt der Client nicht mehr, denn er ist weg.

Das Programm unten hat einen langsamen Handler. `Task.Delay` steht stellvertretend für eine lange Abfrage. Der Client bricht nach 200 Millisekunden ab. Eine Zeile im ausgeblendeten Teil gibt dem Server nur Zeit, seine Meldung zu schreiben.

## Achtung

:::warning[Achtung]
<Misconception id="m17-l09-scoped-lives-whole-app" />

**„Ein Scoped-Service lebt in einer Web-App so lange wie die Anwendung.“** Der Scope einer Web-App ist die einzelne Anfrage. Ein Scoped-Service lebt eine Anfrage lang. So lange wie die App lebt ein Singleton, und darum muss er mit gleichzeitigen Anfragen zurechtkommen.
:::

:::warning[Achtung]
<Misconception id="m17-l09-cancellation-automatic" />

**„Der Abbruch einer Anfrage stoppt die Datenbankabfrage auch ohne weitergereichten Token.“** Das Framework setzt nur den Token. Eine Abfrage, die ihn nie bekommt, läuft bis zum Ende, und ihr Ergebnis wird verworfen.
:::

<details>
<summary>Vertiefung: Dieselbe Anfrage, viele Threads (optional)</summary>

Die Arbeit einer Anfrage kann nach jedem `await` auf einem anderen Thread weiterlaufen (Modul 13). Der Scope hängt nicht am Thread, sondern an der Anfrage: `RequestServices` zeigt in der ganzen Anfrage auf denselben Provider. Der `HttpContext` selbst ist dagegen nicht für parallelen Zugriff ausgelegt. Die Empfehlungen zu `HttpContext` und zum Abbruch stehen in [ASP.NET Core Best Practices](https://learn.microsoft.com/aspnet/core/fundamentals/best-practices).

</details>

## Zusammenfassung

Das Framework legt für jede Anfrage einen DI-Scope an. Ein Scoped-Service lebt darin genau eine Anfrage lang, auch der `DbContext`. Ein Handler bekommt registrierte Services als Parameter, mit `[FromServices]` ausdrücklich und mit `[FromKeyedServices]` nach Schlüssel. Ein Singleton wird von allen Anfragen geteilt und muss thread-sicher sein. Ein `CancellationToken`-Parameter ist an den Abbruch der Anfrage gebunden. Er stoppt Datenbankaufrufe nur, wenn der Handler ihn weitergibt.
