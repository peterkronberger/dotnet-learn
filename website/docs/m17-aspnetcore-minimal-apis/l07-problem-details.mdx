## Ein Format für alle Fehler

Bisher antwortet die API auf Fehler uneinheitlich. Die Validierung aus Lektion 5 schickt einen Body mit Fehlern, `TypedResults.NotFound()` schickt gar keinen, und eine unbehandelte Exception ergibt `500` ohne brauchbaren Body. Ein Client, der die API aufruft, müsste jede dieser Antworten anders lesen.

Dafür gibt es ein Standardformat: <Term id="problem-details">Problem Details</Term> (RFC 9457). Die Antwort ist JSON mit dem Content-Type `application/problem+json` und diesen Feldern:

| Feld | Bedeutung |
| --- | --- |
| `type` | Eine Adresse, die die Art des Problems benennt |
| `title` | Eine kurze Beschreibung der Art des Problems |
| `status` | Der Statuscode der Antwort |
| `detail` | Eine Erklärung zu diesem einen Fall |
| `errors` | Erweiterung von ASP.NET Core bei Validierungsfehlern: je Eigenschaft eine Liste von Meldungen |

Außerdem kann eine Antwort weitere Felder haben. ASP.NET Core ergänzt zum Beispiel `traceId`, eine Kennung der Anfrage, die sich bei jeder Anfrage ändert. Die Ausgaben unten lassen sie weg, damit sie bei jedem Lauf gleich sind.

Ein Handler kann ein Problem selbst erzeugen: `TypedResults.Problem(…)` für beliebige Fehler, `TypedResults.ValidationProblem(errors)` für Validierungsfehler mit dem Feld `errors`. Aber nicht jede Fehlerantwort entsteht in einem Handler. Eine unbekannte Route, ein leeres `404` oder eine Exception haben keinen Handler, der sie formatiert. Dafür richtest du die Fehlerbehandlung einmal zentral ein, mit drei Aufrufen:

1. `builder.Services.AddProblemDetails()` registriert den Dienst, der Problem Details schreibt.
2. `app.UseExceptionHandler()` fügt die <Term id="exception-handler-middleware">Exception-Handler-Middleware</Term> hinzu. Sie fängt eine unbehandelte Exception und schreibt eine `500`-Antwort als Problem Details.
3. `app.UseStatusCodePages()` ergänzt für Antworten mit einem Statuscode von 400 bis 599 und ohne Body einen Body, hier also Problem Details.

<Forward concepts={['Middleware']} lesson="m17-l08" />

Das Programm unten hat drei Endpoints: `GET /incidents/{id}` mit `TypedResults.NotFound()`, `PUT /incidents/{id}/status` mit `Results.ValidationProblem` und `GET /crash`, das eine Exception wirft. Die Meldung der Exception enthält absichtlich ein Passwort, um zu zeigen, dass sie nicht in der Antwort landet.

## Eigene Zuordnung mit IExceptionHandler

<Since dotnet="8" /> Manche Exceptions bedeuten einen Fehler des Clients, nicht des Servers. Wirft ein Handler eine `IncidentNotFoundException`, soll die Antwort `404` sein, nicht `500`. Dafür implementierst du die Schnittstelle `IExceptionHandler` mit der Methode `TryHandleAsync(httpContext, exception, cancellationToken)`:

- Ist der Handler für die Exception zuständig, schreibt er die komplette Antwort (Statuscode und Body) und gibt `true` zurück.
- Ist er nicht zuständig, gibt er `false` zurück. Dann fragt die Middleware den nächsten Handler.

Du registrierst ihn mit `builder.Services.AddExceptionHandler<T>()`. Mehrere Handler laufen in der Reihenfolge der Registrierung. Registrieren allein reicht nicht: Aufgerufen werden sie von `UseExceptionHandler()`. Gibt keiner `true` zurück, greift die Standardantwort aus Problem Details ([IExceptionHandler](https://learn.microsoft.com/aspnet/core/fundamentals/error-handling#iexceptionhandler)).

Das Beispiel nutzt den Dienst `IProblemDetailsService`, den `AddProblemDetails()` registriert. Er schreibt dasselbe Format wie bei allen anderen Fehlern. Der Handler bekommt ihn über den Konstruktor (Modul 15).

## Achtung

:::warning[Achtung]
<Misconception id="m17-l07-error-response-shows-exception" />

**„Eine gute Fehlerantwort enthält die Exception-Meldung und den Stacktrace, damit der Client den Fehler findet.“** Beides verrät Interna wie Pfade, Tabellennamen oder Versionen, und der Client kann damit nichts reparieren. Die Antwort nennt Statuscode und Titel. Meldung und Stacktrace gehören ins Log des Servers.
:::

:::warning[Achtung]
<Misconception id="m17-l07-try-catch-in-every-handler" />

**„Jeder Handler braucht ein eigenes `try`/`catch`, das den Fehler formatiert.“** Dann hat jeder Handler sein eigenes Format, und ein vergessener Handler liefert ein anderes. Eine zentrale Stelle behandelt alle Fälle gleich. `try`/`catch` bleibt sinnvoll, wenn ein Handler eine bestimmte Exception selbst behandeln kann.
:::

## Zusammenfassung

Problem Details (RFC 9457) ist das Standardformat für Fehlerantworten: `application/problem+json` mit `type`, `title`, `status`, `detail` und bei Validierungsfehlern `errors`. `AddProblemDetails` registriert den Dienst, `UseExceptionHandler` macht aus einer unbehandelten Exception eine `500`-Antwort, und `UseStatusCodePages` füllt leere Fehlerantworten. Mit `IExceptionHandler` ordnest du eine Exception einem Statuscode zu. Die Antwort enthält keine Meldung und keinen Stacktrace, denn beides gehört ins Log.
