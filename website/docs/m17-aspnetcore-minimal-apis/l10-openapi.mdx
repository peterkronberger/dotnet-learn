## Eine API, die sich selbst beschreibt

Ein Client, der deine API aufrufen will, muss wissen, welche Pfade es gibt, welche Methoden sie annehmen, welche Parameter und Bodys sie erwarten und welche Antworten zurückkommen. Das lässt sich aufschreiben, aber ein Text veraltet, sobald sich der Code ändert. <Term id="openapi">OpenAPI</Term> ist ein Standard, der dieselben Angaben maschinenlesbar festhält ([Overview of OpenAPI support in ASP.NET Core API apps](https://learn.microsoft.com/aspnet/core/fundamentals/openapi/overview)). Die Beschreibung heißt <Term id="openapi-document">OpenAPI-Dokument</Term> und ist JSON (Lektion 2) oder YAML. Werkzeuge lesen sie und erzeugen daraus Dokumentation, Client-Code oder Tests.

ASP.NET Core schreibt das Dokument nicht von Hand, sondern erzeugt es aus den Endpoints der App. Dafür ist das Paket `Microsoft.AspNetCore.OpenApi` nötig, und zwei Aufrufe <Since dotnet="9" />:

- `builder.Services.AddOpenApi()` registriert die Dienste, die das Dokument erzeugen.
- `app.MapOpenApi()` legt einen Endpoint an, der das Dokument als JSON ausliefert, standardmäßig unter `/openapi/v1.json`.

Der Inhalt kommt aus dem, was die App über jeden Endpoint weiß: Pfad und Methode, die Parameter des Handlers, der Body und seine Attribute, der Rückgabetyp. Dazu kommen <Term id="endpoint-metadata">Metadaten</Term>, die du an den Endpoint hängst:

- `WithName("…")` setzt die Operation-Id, den eindeutigen Namen der Operation.
- `WithSummary("…")` setzt eine Kurzbeschreibung, `WithDescription("…")` eine längere.
- `WithTags("…")` ordnet die Operation einer Gruppe zu. Werkzeuge nutzen das zum Sortieren.
- `Produces<T>(…)` und `ProducesProblem(…)` nennen zusätzliche Antworten, die der Rückgabetyp nicht zeigt.

([Include OpenAPI metadata in an ASP.NET Core app](https://learn.microsoft.com/aspnet/core/fundamentals/openapi/include-metadata))

Metadaten beschreiben nur. Sie ändern das Verhalten des Endpoints nicht: Steht dort `418`, der Handler sendet aber `200`, bleibt es bei `200`.

Antworten musst du meist nicht selbst nennen. Ein typisiertes Ergebnis (Lektion 6) bringt seine Metadaten mit, und bei `Results<Ok<T>, NotFound>` steht je Typ ein Eintrag im Dokument. Auch Attribute zur Validierung (Lektion 5) wirken: `[MaxLength(32)]` wird zur Grenze `maxLength: 32` im Schema. Das Dokument beschreibt die Grenze, die Prüfung selbst bleibt Sache der Validierung.

Das Programm unten baut zwei Endpoints mit Namen und Kurzbeschreibung, ruft das Dokument ab und liest es mit `JsonDocument` (Lektion 2). Es druckt nur einen kleinen, stabilen Teil: die Version, die Pfade mit Name, Kurzbeschreibung und Antwortcodes und die Grenze aus dem Attribut.

:::

## Oberflächen, YAML und Build

Drei Randthemen, nur kurz und nur mit Namen:

- **Oberflächen:** ASP.NET Core erzeugt nur das Dokument. Oberflächen zum Ausprobieren, etwa Swagger UI oder Scalar, gehören nicht dazu. Sie sind eigene Pakete und lesen das Dokument nur.
- **YAML:** Mit `app.MapOpenApi("/openapi/{documentName}.yaml")` liefert die App dasselbe Dokument als YAML.
- **Beim Build erzeugen:** Das Paket `Microsoft.Extensions.ApiDescription.Server` schreibt das Dokument beim Build in eine Datei.

**Sicherheit:** Das Dokument nennt jeden Pfad, jeden Parameter und jede Antwort der API. Für jemanden, der die API ausspäht, ist es eine fertige Landkarte. Darum entscheidest du bewusst, in welchen Umgebungen es erreichbar ist. Lektion 12 erledigt das. Die Vorlage von ASP.NET Core ruft `MapOpenApi` nur in der Entwicklung auf.

## Achtung

:::warning[Achtung]
<Misconception id="m17-l10-openapi-is-swagger-ui" />

**„OpenAPI ist die Weboberfläche, auf der man Endpunkte ausprobiert.“** OpenAPI ist das Format des Dokuments, JSON oder YAML. Oberflächen wie Swagger UI oder Scalar lesen es nur und zeigen es an. ASP.NET Core liefert das Dokument, aber keine Oberfläche.
:::

:::warning[Achtung]
<Misconception id="m17-l10-document-written-by-hand" />

**„Das OpenAPI-Dokument schreibe ich von Hand.“** ASP.NET Core erzeugt es aus Endpoints, Parametern, Ergebnistypen und Metadaten. Von Hand ergänzt du nur, was der Code nicht zeigt, etwa Kurzbeschreibungen.
:::

<details>
<summary>Vertiefung: Schema, Komponenten und Versionen (optional)</summary>

Ein OpenAPI-Dokument hat feste Hauptteile: `paths` ordnet jedem Pfad die Operationen je HTTP-Methode zu, und `components` sammelt wiederverwendbare Schemas, etwa den Typ `StatusChange`. Die Operationen verweisen darauf. Die Version steht im Feld `openapi`. ASP.NET Core erzeugt seit .NET 10 Dokumente der Version 3.1 und seit .NET 11 der Version 3.2 und lässt sich auf frühere Versionen einstellen ([Generate OpenAPI documents](https://learn.microsoft.com/aspnet/core/fundamentals/openapi/aspnetcore-openapi)). Wer Dokumente an andere Werkzeuge gibt, prüft daher, welche Version diese lesen.

</details>

## Zusammenfassung

Ein OpenAPI-Dokument beschreibt eine HTTP-API maschinenlesbar. ASP.NET Core erzeugt es zur Laufzeit aus den Endpoints: `AddOpenApi` registriert die Dienste, `MapOpenApi` liefert das JSON unter `/openapi/v1.json` aus. Typisierte Ergebnisse und Validierungsattribute fließen automatisch ein, `WithName`, `WithSummary` und `Produces` ergänzen Metadaten. Metadaten beschreiben nur und ändern das Verhalten nicht. Oberflächen wie Swagger UI sind getrennte Werkzeuge. Weil das Dokument die ganze API zeigt, entscheidest du, wo es erreichbar ist.
