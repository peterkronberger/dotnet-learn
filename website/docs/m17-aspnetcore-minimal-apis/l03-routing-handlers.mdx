## Eine Web-App in wenigen Zeilen

<Term id="asp-net-core">ASP.NET Core</Term> ist das Framework von .NET für Web-Anwendungen. Es baut auf dem generischen Host aus Modul 15 auf: Die App wird mit einem Builder zusammengesetzt, gebaut und gestartet. Eine <Term id="minimal-api">Minimal API</Term> ist die Art, mit sehr wenig Code eine HTTP-API zu schreiben. Das Grundgerüst hat vier Schritte:

1. `WebApplication.CreateBuilder(args)` erzeugt den Builder. Er nimmt Konfiguration und Services auf, wie du es aus Modul 15 kennst.
2. `builder.Build()` baut daraus die `WebApplication`.
3. Mit Aufrufen wie `app.MapGet(…)` legst du <Term id="endpoint">Endpoints</Term> an.
4. `app.Run()` startet die App. Sie wartet dann auf Anfragen.

Ein Webserver, der die Anfragen entgegennimmt, gehört dazu. Er heißt Kestrel und läuft ohne dein Zutun mit. Lektion 12 erklärt ihn.

Ein Endpoint verbindet drei Dinge: eine HTTP-Methode (Lektion 1), eine <Term id="route-template">Routenvorlage</Term> für den Pfad und einen <Term id="route-handler">Handler</Term>. Der Handler ist die Methode oder das Lambda, das läuft, wenn beide passen. Für die Methoden gibt es `MapGet`, `MapPost`, `MapPut` und `MapDelete`. Das <Term id="routing">Routing</Term> sucht zu jeder Anfrage den passenden Endpoint.

Der Rückgabewert des Handlers wird zur Antwort:

- Ein `string` wird Text mit dem Inhaltstyp `text/plain`.
- Ein Objekt, ein Record oder eine Liste wird mit den Web-Einstellungen aus Lektion 2 zu JSON (camelCase).
- Ein asynchroner Handler gibt `Task<T>` zurück. Die Antwort enthält den Wert `T`.

Ein Handler ist ein Lambda (Modul 10) oder eine benannte Methode. Beide gibst du `MapGet` als zweites Argument.

Das Programm legt sechs Endpoints an und schickt Anfragen daran. Der Teil, der den Server im Speicher startet und die Anfragen sendet, ist ausgeblendet. Er läuft mit, und die Ausgabe zeigt je Anfrage die Zeile `> GET …`, die Antwort (`< 200 OK`), den Inhaltstyp und den Body.

## Routenvorlagen, Parameter und Einschränkungen

Eine Routenvorlage ist ein Muster für den Pfad. Text steht für sich selbst. Ein Teil in geschweiften Klammern ist ein <Term id="route-parameter">Routenparameter</Term>: Er passt auf einen beliebigen Pfadteil, und der Wert geht an den Handler-Parameter mit demselben Namen. Ist der Parameter ein `int`, wandelt ASP.NET Core den Text um.

Eine <Term id="route-constraint">Routeneinschränkung</Term> steht hinter einem Doppelpunkt: `{id:int}` passt nur auf ganze Zahlen, `{name:alpha}` nur auf Buchstaben von `a` bis `z`. Eine Einschränkung wählt aus, welche Route passt. Sie prüft keine Eingabe: Passt der Wert nicht, passt die Route nicht, und ohne weitere Route kommt `404`. Fehlerantworten für ungültige Eingaben (`400`) sind das Thema der nächsten Lektionen.

Passen mehrere Routen zu einer Anfrage, entscheidet nicht die Reihenfolge der `Map…`-Aufrufe. Das Routing nimmt die spezifischste Vorlage:

- Eine Vorlage mit mehr Teilen ist spezifischer.
- Ein Teil aus festem Text ist spezifischer als ein Parameter.
- Ein Parameter mit Einschränkung ist spezifischer als einer ohne.

Gäbe es zwei gleich spezifische Treffer, wäre die Anfrage mehrdeutig, und die App meldet einen Fehler.

Mit einer <Term id="route-group">Routengruppe</Term> (`MapGroup`) fasst du Endpoints mit gemeinsamem Präfix zusammen. Die Gruppe stellt ihr Präfix jeder Vorlage voran und hat selbst `MapGet` und die anderen Methoden.

:::info[Vorhersage]
Die drei `/incidents`-Routen sind absichtlich in dieser Reihenfolge angelegt: zuerst die allgemeine, zuletzt die spezifische. Welcher Handler antwortet auf `/incidents/latest`, `/incidents/7` und `/incidents/bob`? Was antwortet `/users/42`? Notiere deinen Tipp und lies dann die Lösung.
:::

1. **Text schlägt Parameter:** `/incidents/latest` passt auf `{name}` und auf `latest`. `{id:int}` entfällt, weil `latest` keine Zahl ist. Die Vorlage mit festem Text `latest` ist spezifischer als `{name}`. Obwohl `{name}` zuerst angelegt wurde, gewinnt sie nicht.
2. **Einschränkung schlägt Parameter:** `/incidents/7` passt auf `{name}` und auf `{id:int}`. Die Vorlage mit Einschränkung ist spezifischer.
3. **Rest:** `bob` ist keine Zahl, `{id:int}` entfällt, `{name}` bleibt.
4. **Gruppe:** `users.MapGet("/", …)` hat die Vorlage `/users`, `users.MapGet("/{name:alpha}", …)` die Vorlage `/users/{name:alpha}`.
5. **Einschränkung `alpha`:** `42` besteht aus Ziffern. Die Route passt nicht: `404 Not Found`.

**Was passiert, wenn …** du die Aufrufe tauschst und `/incidents/latest` zuerst anlegst? Das Ergebnis bleibt gleich. Die Reihenfolge entscheidet nicht.

</details>

## Achtung

:::warning[Achtung]
<Misconception id="m17-l03-route-order-decides" />

**„Die Reihenfolge der `Map…`-Aufrufe entscheidet, welcher Endpoint passt.“** Das Routing betrachtet alle Endpoints gleichzeitig und nimmt die spezifischste Vorlage. Fester Text schlägt einen Parameter, ein Parameter mit Einschränkung schlägt einen ohne.
:::

:::warning[Achtung]
<Misconception id="m17-l03-constraint-validates-input" />

**„Mit `{id:int}` prüft ASP.NET Core die Eingabe und meldet einen Fehler.“** Die Einschränkung entscheidet nur, ob die Route passt. Bei `/incidents/abc` gibt es ohne andere Route die Antwort 404, keine Fehlermeldung mit 400.
:::

<details>
<summary>Vertiefung: Wenn zwei Routen gleich spezifisch sind (optional)</summary>

Die Rangfolge der Vorlagen steht im Abschnitt zur Routenpriorität von [Routing in ASP.NET Core](https://learn.microsoft.com/aspnet/core/fundamentals/routing). Haben zwei Endpoints dieselbe Priorität und passen beide, wirft das Routing eine Ausnahme wegen einer mehrdeutigen Übereinstimmung. Eine Reihenfolge, die das auflöst, gibt es für Minimal APIs nicht. Du machst dann eine der Vorlagen spezifischer oder änderst eine Route.

</details>

## Zusammenfassung

Eine Minimal API entsteht aus `WebApplication.CreateBuilder`, `Build`, den `Map…`-Aufrufen und `Run`. Ein Endpoint verbindet eine Methode, eine Routenvorlage und einen Handler. Der Rückgabewert des Handlers wird zur Antwort: Text als `text/plain`, Objekte als JSON. Routenparameter liefern Pfadteile, Einschränkungen wie `int` entscheiden, ob die Route passt. Bei mehreren Treffern gewinnt die spezifischste Vorlage, nicht der erste Aufruf. `MapGroup` stellt allen Endpoints ein Präfix voran.
