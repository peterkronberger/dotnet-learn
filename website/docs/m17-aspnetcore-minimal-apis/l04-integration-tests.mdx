## Unit-Test und Integrationstest

Ein Unit-Test (Modul 14) prüft eine kleine Einheit für sich, meist mit Test-Doubles für ihre Abhängigkeiten. Ein <Term id="integration-test">Integrationstest</Term> lässt mehrere Teile zusammenarbeiten. Für einen Endpoint heißt das: Eine echte HTTP-Anfrage läuft durch die ganze App. Routing, Parameter, Handler, Datenbank und JSON werden gemeinsam geprüft. Ein Unit-Test des Handlers sieht den Statuscode und die JSON-Namen nicht, ein Integrationstest sieht sie. Dafür ist er langsamer und braucht mehr Vorbereitung. Eine gute Testsuite hat viele schnelle Unit-Tests und weniger Integrationstests.

Du musst die App dafür nicht auf einem Port starten. Das Paket `Microsoft.AspNetCore.Mvc.Testing` bringt die Klasse <Term id="web-application-factory">`WebApplicationFactory<TEntryPoint>`</Term> mit. Sie startet die echte App mit einem <Term id="test-server">Testserver</Term>, der im Speicher des Testprozesses läuft. Mit `CreateClient()` bekommst du einen <Term id="http-client">`HttpClient`</Term>, dessen Anfragen direkt in der Pipeline der App ankommen: ohne Netzwerk und ohne Port.

Die Fabrik braucht einen Typ aus der App, meist die Klasse `Program` von `Program.cs`. Sie ist aus Top-Level-Statements entstanden und für andere Projekte nicht sichtbar. Die Zeile `public partial class Program;` am Ende von `Program.cs` macht sie sichtbar.

Im xUnit-Test (Modul 14) übergibst du die Fabrik mit `IClassFixture<T>`: xUnit erzeugt sie einmal für alle Tests der Klasse, gibt sie dem Konstruktor und gibt sie danach frei. Im Test:

1. **Client holen:** `factory.CreateClient()`.
2. **Anfrage senden:** `client.GetAsync(pfad, token)` liefert die Antwort. `GetFromJsonAsync<T>(pfad, token)` sendet und liest den JSON-Body gleich als `T`. Beide kennen die Web-Einstellungen aus Lektion 2.
3. **Prüfen:** `Assert.Equal` auf den Statuscode (`response.StatusCode`) und auf den Inhalt.

Das Token kommt wie in Lektion 12 von Modul 14 aus `TestContext.Current.CancellationToken`.

Services lassen sich im Test ersetzen. `WithWebHostBuilder` liefert eine Fabrik mit zusätzlicher Konfiguration, und `ConfigureTestServices` registriert einen Service, der den der App ersetzt, zum Beispiel ein Test-Double. Die Konfiguration läuft nach dem Code in `Program.cs`.

Das Beispiel hat einen Endpoint `GET /failures/{user}`, der einen `IFailureCounter` aus der Dependency Injection nutzt. Es hat drei Tests: eine Anfrage mit dem echten Service, eine mit einem Fake und eine auf eine Route, die es nicht gibt.

## Eine frische Testdatenbank

Ein Test soll bei jedem Lauf dieselben Daten sehen. Die API von SecLog liest `ConnectionStrings:SecLog` aus `appsettings.json`: `Data Source=seclog.db`. Im Test soll sie eine eigene SQLite-Datei nutzen. Die Fabrik kann die Konfiguration überschreiben: `UseSetting("ConnectionStrings:SecLog", …)` in `ConfigureWebHost`. Einstellungen aus dem Test haben Vorrang vor `appsettings.json` (Modul 15).

Der Rest ist in `SecLogApiFactory` zusammengefasst:

1. **Ordner anlegen:** `Directory.CreateTempSubdirectory` erzeugt einen neuen Ordner. Die Datei darin gehört nur diesem Testlauf.
2. **Datenbank zeigen:** `UseSetting` setzt den Verbindungsstring auf diese Datei.
3. **Vorbereiten:** `CreateHost` baut den Host. Danach legt `Database.Migrate()` das Schema an (Modul 16), und zwei Vorfälle aus den SecLog-Beispieldaten werden gespeichert.
4. **Aufräumen:** `Dispose` gibt die SQLite-Verbindungen frei und löscht den Ordner.

## Achtung

:::warning[Achtung]
<Misconception id="m17-l04-integration-test-needs-running-server" />

**„Für einen Integrationstest muss die App vorher auf einem Port gestartet werden.“** `WebApplicationFactory` startet die App selbst, mit einem Testserver im Speicher. Der Test braucht weder einen Port noch ein Netzwerk.
:::

:::warning[Achtung]
<Misconception id="m17-l04-test-uses-production-database" />

**„Der Test nutzt die Datenbank der echten App.“** Die App liest ihre Konfiguration auch im Test. Ohne Eingriff zeigt sie auf die Datenbank aus `appsettings.json`. Darum überschreibt die Fabrik den Verbindungsstring mit einer frischen Testdatei.
:::

<details>
<summary>Vertiefung: Konfiguration im Test überschreiben (optional)</summary>

Die Fabrik bietet mehrere Wege, die App im Test zu ändern: `UseSetting` und `ConfigureAppConfiguration` für Konfiguration, `ConfigureTestServices` für Services. Das Vorgehen ist im Abschnitt „Customize WebApplicationFactory“ von [Integration tests in ASP.NET Core](https://learn.microsoft.com/aspnet/core/test/integration-tests) beschrieben. Für Tests mit einer Datenbank nennt EF Core mehrere Strategien. SQLite als echte, aber leichte Datenbank ist eine davon ([Choosing a testing strategy](https://learn.microsoft.com/ef/core/testing/choosing-a-testing-strategy)).

</details>

## Zusammenfassung

Ein Integrationstest schickt eine echte Anfrage durch die ganze App und prüft Routing, Handler und JSON zusammen. `WebApplicationFactory<Program>` startet die App mit einem Testserver im Speicher, `CreateClient()` liefert den passenden `HttpClient`. Im Test prüfst du Statuscode und Body, etwa mit `GetFromJsonAsync<T>`. Mit `ConfigureTestServices` ersetzt du Services, mit einer eigenen Verbindung eine Testdatenbank. Eine Klassen-Fixture teilt die Fabrik zwischen den Tests einer Klasse.
