## Client und Server

Bei den meisten Programmen im Netz arbeiten zwei Seiten zusammen. Der <Term id="client-server">Client</Term> schickt eine Anfrage, der Server beantwortet sie. Ein Browser ist ein Client, ein Programm, das Daten abruft, ebenso. Der Server wartet auf Anfragen und liefert Antworten. Beide sprechen über ein festes Protokoll. Für das Web ist das <Term id="http">HTTP</Term>. Bei HTTPS läuft dieselbe Sprache verschlüsselt. Die Verschlüsselung selbst ist hier kein Thema.

HTTP ist zustandslos: Der Server behält zwischen zwei Anfragen nichts von der ersten, was zur zweiten gehört. Jede Anfrage enthält alles, was der Server braucht, um sie zu beantworten.

## Die Adresse einer Anfrage

Der Client nennt, welche Ressource er meint, mit einer <Term id="url">URL</Term>. Sie hat vier Teile, hier an `https://example.com/incidents?user=bob`:

- **Schema:** `https` – das Protokoll.
- **Host:** `example.com` – der Server.
- **Pfad:** `/incidents` – die Ressource auf dem Server.
- **Query:** `user=bob` – Angaben nach dem `?`, mit denen der Client die Antwort eingrenzt.

Im Beispiel dieser Lektion fehlen Schema und Host: Die Anfragen gehen in dasselbe Programm. Du siehst nur den Pfad.

## Anfrage und Antwort

Eine <Term id="http-request">Anfrage</Term> besteht aus vier Teilen:

1. **Anfragezeile:** <Term id="http-method">Methode</Term>, Pfad und Protokollversion, zum Beispiel `GET /incidents/1 HTTP/1.1`.
2. **<Term id="http-header">Header</Term>:** Zeilen der Form `Name: Wert` mit Zusatzangaben. `Accept` nennt das Format, das der Client erwartet. `Content-Type` nennt das Format des Bodys.
3. **Leerzeile:** Sie trennt die Header vom Body.
4. **Body:** der Inhalt, optional. Eine Anfrage zum Lesen hat meist keinen.

Eine <Term id="http-response">Antwort</Term> hat denselben Aufbau, nur mit einer Statuszeile: Protokollversion, <Term id="http-status-code">Statuscode</Term> und ein Kurztext, zum Beispiel `200 OK`. Dann folgen Header und ein optionaler Body.

Der Body ist in diesem Modul meist JSON-Text. Hier genügt: Es ist Text mit Namen und Werten.

1. **Anfragezeile lesen:** Jede Gruppe beginnt mit der Methode und dem Pfad.
2. **Statuscode prüfen:** `200` beim Lesen von Vorfall 1, `404` bei Vorfall 99, den es nicht gibt.

## Die vier Methoden

Die Methode sagt, was der Server mit der Ressource tun soll:

| Methode | Zweck | Beispiel im Lauf |
| --- | --- | --- |
| `GET` | Eine Ressource lesen | `GET /incidents/1` |
| `POST` | Daten zur Verarbeitung schicken, zum Beispiel etwas Neues anlegen | `POST /incidents` |
| `PUT` | Eine Ressource durch den gesendeten Zustand ersetzen | `PUT /incidents/1/status` |
| `DELETE` | Eine Ressource entfernen | `DELETE /incidents/2` |

Zwei Eigenschaften unterscheiden die Methoden. Eine Methode ist **sicher**, wenn sie den Zustand des Servers nicht ändert. Von den vier ist nur `GET` sicher. Eine Methode ist <Term id="idempotency">idempotent</Term>, wenn mehrfaches Senden derselben Anfrage den Zustand so ändert wie ein einziges Senden. `GET`, `PUT` und `DELETE` sind idempotent, `POST` nicht. Sicher ist also strenger als idempotent: Jede sichere Methode ist idempotent, aber `PUT` und `DELETE` sind es, ohne sicher zu sein.

Idempotenz betrifft den Zustand, nicht den Wortlaut der Antwort. Das zweite `DELETE` im Lauf hat eine andere Antwort (`404`) als das erste (`204`). Der Zustand ist nach beiden gleich: Vorfall 2 gibt es nicht.

Das hilft bei unsicheren Netzen. Ein Client, der eine Antwort nicht erhält, weiß nicht, ob die Anfrage ankam. Bei `PUT` kann er sie gefahrlos wiederholen. Bei `POST` kann er dadurch ein zweites Objekt anlegen.

## Statuscodes

Der Statuscode ist eine dreistellige Zahl. Die erste Ziffer gibt die Klasse an:

| Klasse | Bedeutung | Codes im Lauf |
| --- | --- | --- |
| 1xx | Information | – |
| 2xx | Erfolg | `200 OK`, `201 Created`, `204 No Content` |
| 3xx | Umleitung | – |
| 4xx | Fehler der Anfrage | `404 Not Found`, `405 Method Not Allowed` |
| 5xx | Fehler im Server | – |

Die Codes, die du in diesem Modul oft siehst:

- `200`: Erfolg, die Antwort hat einen Body.
- `201`: Eine neue Ressource ist entstanden. Der Header `Location` nennt ihre Adresse.
- `204`: Erfolg ohne Body.
- `400`: Die Anfrage ist fehlerhaft, zum Beispiel ungültiger Inhalt.
- `401`: Die Ressource verlangt eine Anmeldung, die fehlt.
- `403`: Der Server verweigert die Anfrage.
- `404`: Die Ressource gibt es nicht.
- `500`: Im Server ist ein Fehler aufgetreten.

## Achtung

:::warning[Achtung]
<Misconception id="m17-l01-put-and-post-are-same" />

**„`PUT` und `POST` sind austauschbar, beide speichern einfach Daten.“** `PUT` nennt die Ressource und ihren Zielzustand und ist idempotent: Wiederholen ändert nichts mehr. `POST` ist es nicht, jeder Aufruf kann etwas Neues anlegen. Im Lauf legt das zweite `POST` einen weiteren Vorfall an, das zweite `PUT` ändert nichts mehr.
:::

:::warning[Achtung]
<Misconception id="m17-l01-4xx-means-server-broken" />

**„Ein Statuscode 4xx heißt, dass der Server kaputt ist.“** 4xx meldet ein Problem der Anfrage: Die Ressource fehlt (`404`), die Methode passt nicht (`405`), der Inhalt ist ungültig (`400`). Der Server arbeitet und sagt das deutlich. Fehler im Server haben die Klasse 5xx.
:::

<details>
<summary>Vertiefung: Wo die Regeln stehen (optional)</summary>

Die Bedeutung der Methoden, ihre Eigenschaften „sicher“ und „idempotent“ und die Statuscodes legt die Spezifikation „HTTP Semantics“ fest ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110)). Die .NET-Aufzählung `HttpStatusCode` folgt ihrem Abschnitt 15 ([HttpStatusCode](https://learn.microsoft.com/dotnet/api/system.net.httpstatuscode)). Neben den vier Methoden dieser Lektion gibt es weitere, zum Beispiel `PATCH` für Teiländerungen. Sie sind hier nicht dran.

</details>

## Zusammenfassung

Ein Client schickt eine Anfrage mit Methode, Pfad, Headern und optionalem Body. Der Server antwortet mit Statuscode, Headern und optionalem Body. HTTP ist zustandslos. `GET` liest und ist sicher. `PUT` und `DELETE` sind idempotent, `POST` ist es nicht. Die erste Ziffer des Statuscodes nennt die Klasse: 2xx Erfolg, 4xx Fehler der Anfrage, 5xx Fehler im Server.
