## Konventionen: EF Core rät mit

In der letzten Lektion hast du eine Klasse `Incident` mit `Id` und einem `DbContext` geschrieben und keine Zeile Konfiguration. Trotzdem hat EF Core eine passende Tabelle angelegt. Das Wissen darüber, wie Klassen, Tabellen, Spalten und Schlüssel zusammengehören, heißt <Term id="ef-core-model">Modell</Term>. EF Core baut es aus der Klasse, und ohne weitere Angaben gelten die <Term id="ef-core-convention">Konventionen</Term> ([Creating and configuring a model](https://learn.microsoft.com/ef/core/modeling/)). Die wichtigsten:

- **Tabellenname:** der Name der `DbSet`-Eigenschaft, hier `Incidents`.
- **Schlüssel:** eine Eigenschaft mit dem Namen `Id` oder `<Typname>Id` ist der Primärschlüssel. Hat sie den Typ `int`, vergibt die Datenbank die Werte ([Keys](https://learn.microsoft.com/ef/core/modeling/keys)).
- **Pflicht oder optional:** Bei aktivierten Nullable Reference Types ist eine Eigenschaft vom Typ `string` Pflicht, `string?` ist optional. Ein Werttyp wie `int` ist Pflicht ([Required and optional properties](https://learn.microsoft.com/ef/core/modeling/entity-properties#required-and-optional-properties)).

Der Befehl ist SQL. `CREATE TABLE` legt eine Tabelle an. In den Klammern steht je Spalte ein Name, ein Typ und eine Regel:

1. **Name:** Die Tabelle heißt wie die `DbSet`-Eigenschaft: `Incidents`.
2. **Schlüssel:** `PRIMARY KEY` kennzeichnet `Id` als Primärschlüssel. `AUTOINCREMENT` heißt: Die Datenbank zählt die Werte selbst hoch.

4. **Optional:** `NULL` heißt, der Wert darf fehlen. `Note` ist `string?`.

**Was passiert, wenn …** du `required` bei `User` entfernst und `string User { get; set; } = "";` schreibst? Die Spalte bleibt `NOT NULL`, denn der Typ `string` ohne `?` entscheidet, nicht das Schlüsselwort `required`.

## Data Annotations und Fluent API

Die Konventionen passen nicht immer. Dann konfigurierst du das Modell selbst, auf zwei Wegen:

1. **<Term id="data-annotation">Data Annotations</Term>:** Attribute (`m14-l06`) an der Klasse oder Eigenschaft. Aus dem Namespace `System.ComponentModel.DataAnnotations` kommen zum Beispiel `[Key]`, `[Required]` und `[MaxLength(64)]`. `[Table("…")]` und `[Column("…")]` ändern den Namen von Tabelle und Spalte.
2. **<Term id="fluent-api">Fluent API</Term>:** Aufrufe in der Methode `OnModelCreating`, die du im `DbContext` überschreibst. Der `ModelBuilder` hat dafür Methoden wie `Entity<T>()`, `HasKey`, `Property(…).IsRequired()`, `HasMaxLength` und `HasIndex`.

Die Fluent API kann alles, was die Annotations können, und mehr. Für größere Modelle lässt sich die Konfiguration je Entity-Klasse in eine Klasse auslagern, die `IEntityTypeConfiguration<T>` implementiert. Sie wird hier nur genannt, denn die Lektionen dieses Moduls brauchen sie nicht.

Ein <Term id="composite-key">zusammengesetzter Schlüssel</Term> besteht aus mehr als einer Eigenschaft. Dafür gibt es nur die Fluent API: `HasKey(x => new { x.A, x.B })`. Ein <Term id="database-index">Index</Term> hilft der Datenbank, Zeilen nach einer Spalte schnell zu finden, ohne jede Zeile zu prüfen. Du legst ihn mit `HasIndex` fest ([Indexes](https://learn.microsoft.com/ef/core/modeling/indexes)).

## Wer gewinnt?

Legen mehrere Wege dasselbe fest, gilt eine feste Reihenfolge: Die **Fluent API** gewinnt gegen die **Data Annotations**, und diese gewinnen gegen die **Konventionen** ([Creating and configuring a model](https://learn.microsoft.com/ef/core/modeling/#use-the-fluent-api-to-configure-a-model)).

1. **Schlüssel:** `Incident` hat kein `Id`, aber `[Key]` an `Number`. Darum ist `Number` der Schlüssel. Die Tabelle `Assignments` hat zwei Spalten im Schlüssel: `PRIMARY KEY ("IncidentId", "AnalystId")`.
2. **Länge:** `User` hat `[MaxLength(20)]` und `HasMaxLength(64)`. Die Fluent API gewinnt: 64. `Source` hat nur die Annotation: 20.
3. **Index:** `CREATE INDEX` legt den Index auf `User` an.

Das Script zeigt die Länge nicht, weil SQLite sie nicht in der Tabelle festlegt. Darum fragt das Programm das Modell von EF Core direkt ([Maximum length](https://learn.microsoft.com/ef/core/modeling/entity-properties#maximum-length)).

**Was passiert, wenn …** du `[Required]` an `User` entfernst? Nichts ändert sich, denn die Eigenschaft `User` ist ein `string` ohne `?`, und die Konvention macht sie schon zur Pflicht.

</details>

## Achtung

:::warning[Achtung]
<Misconception id="m16-l02-key-needs-attribute" />

**„Ohne `[Key]` hat eine Entität keinen Primärschlüssel.“** Die Konvention findet eine Eigenschaft `Id` oder `<Typname>Id` selbst. `[Key]` oder `HasKey` brauchst du nur, wenn der Name anders ist oder der Schlüssel aus mehreren Eigenschaften besteht.
:::

:::warning[Achtung]
<Misconception id="m16-l02-annotation-beats-fluent-api" />

**„Die Annotation steht direkt an der Eigenschaft, also gewinnt sie.“** Die Position im Code zählt nicht. Die Fluent API überschreibt die Data Annotation, und diese überschreibt die Konvention.
:::

## Zusammenfassung

EF Core baut das Modell aus Konventionen: Der Tabellenname kommt vom `DbSet`, `Id` ist der Schlüssel, und der Nullable-Typ entscheidet über Pflicht und optional. Data Annotations und die Fluent API in `OnModelCreating` überschreiben das. Bei einem Widerspruch gewinnt die Fluent API vor den Annotations und diese vor den Konventionen. Zusammengesetzte Schlüssel und Indizes legst du mit `HasKey` und `HasIndex` fest. `GenerateCreateScript()` zeigt das Ergebnis als SQL.
