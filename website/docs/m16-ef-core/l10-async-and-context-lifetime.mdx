## Datenbankaufrufe sind Ein-/Ausgabe

Eine Abfrage wartet auf die Datenbank, ähnlich wie das Lesen einer Datei. EF Core bietet deshalb zu jeder Methode, die die Datenbank anspricht, eine <Term id="async-query">asynchrone Variante</Term> mit der Endung `Async`. Du wartest sie mit `await` ab (Modul 13). Der Thread blockiert dann nicht, solange die Datenbank arbeitet ([Asynchronous Programming](https://learn.microsoft.com/ef/core/miscellaneous/async)).

Die Varianten gibt es für die Operatoren, die die Abfrage ausführen: `ToListAsync`, `FirstOrDefaultAsync`, `CountAsync`, `AnyAsync` und für das Speichern `SaveChangesAsync`. Für `Where`, `Select` und `OrderBy` gibt es keine, denn sie bauen die Abfrage nur auf. Jede dieser Methoden nimmt am Ende ein `CancellationToken` (`m13-l05`). Wird es abgebrochen, bricht der Aufruf mit einer `OperationCanceledException` ab. Ob eine schon laufende Anweisung sofort stoppt, hängt vom Datenbankanbieter ab. Für Zeilen, die einzeln kommen sollen, liefert `AsAsyncEnumerable()` einen `IAsyncEnumerable<T>`, den `await foreach` liest (`m13-l06`). Dasselbe gibt es für das Anlegen der Datenbank: `EnsureCreatedAsync` und `MigrateAsync`.

## Ein Context ist eine kurze Arbeitseinheit

Ein `DbContext` ist für eine einzige Arbeitseinheit (<Term id="unit-of-work">Unit of Work</Term>) gedacht: erzeugen, Objekte laden und ändern, `SaveChanges` aufrufen, freigeben. Seine Lebensdauer ist darum meist sehr kurz. Er ist nicht thread-sicher: Teile ihn nicht zwischen Threads und warte jeden asynchronen Aufruf ab, bevor du den Context weiter benutzt ([DbContext Lifetime](https://learn.microsoft.com/ef/core/dbcontext-configuration/)).

`AddDbContext<T>` registriert den Context als Scoped-Service (`m15-l03`). Ein Scope ist im Container die Arbeitseinheit: In einem Scope bekommst du immer denselben Context, ein anderer Scope bekommt einen anderen. Der Context braucht dafür einen öffentlichen Konstruktor mit `DbContextOptions<T>`, wie ihn `SecLogDbContext` hat.

Ein Singleton oder ein `BackgroundService` darf keinen Scoped-Service im Konstruktor verlangen (Captive Dependency, `m15-l04`). Er hat zwei Wege. Erstens erzeugt er für jede Arbeitseinheit mit `CreateAsyncScope()` einen Scope und holt den Context daraus. Zweitens registriert man mit `AddDbContextFactory<T>` die <Term id="dbcontext-factory">Fabrik</Term> `IDbContextFactory<T>`, die bei jedem Aufruf einen neuen Context erzeugt. Diesen Context verwaltet der Container nicht, du gibst ihn selbst frei. Die Fabrik passt, wenn keine Scopes pro Arbeitseinheit vorhanden sind, zum Beispiel in einer Blazor-Anwendung.

</details>

## Nicht zwei Operationen zugleich

EF Core unterstützt nicht mehrere parallele Operationen auf demselben Context. Das gilt auch für asynchrone Abfragen, die du gleichzeitig startest. Erkennt EF Core das, wirft es eine `InvalidOperationException` mit einer Meldung, dass eine zweite Operation startete, bevor die erste fertig war. Unerkannt kann es den Zustand des Contexts zerstören. Warte deshalb jeden Aufruf sofort ab oder nimm für parallele Arbeit je einen eigenen Context ([DbContext Lifetime](https://learn.microsoft.com/ef/core/dbcontext-configuration/)).

Das folgende Programm bremst jede Abfrage kurz (die eingeklappte Hilfsklasse), damit sich zwei Operationen sicher überlappen. SQLite würde sie sonst so schnell erledigen, dass der Fehler nicht auftritt. Das ist ein Zufall des Anbieters und keine Erlaubnis.

**Neue Anforderung:** SecLog bekommt seinen Datenbankkontext aus dem DI-Container und greift asynchron auf die Datenbank zu. Das ist eine Umstrukturierung. `Program.cs` registriert `AddDbContext<SecLogDbContext>(o => o.UseSqlite(connectionString))`. Jeder Analyselauf erzeugt einen Scope. Alle synchronen Datenbankaufrufe werden zu den asynchronen und bekommen `stoppingToken`. Die Ausgabe unter `== Database ==` bleibt gleich wie in `seclog-m16-l09`. `ValidateScopes` und `ValidateOnBuild` bleiben an.

1. **Registrieren:** `AddDbContext` macht aus `SecLogDbContext` einen Scoped-Service. Ein weiterer Filter setzt das Log von `Microsoft.EntityFrameworkCore` auf `Warning`, weil der Context aus dem Container jede SQL-Anweisung loggt und die Ausgabe sonst nicht mehr gleich bleibt.

## Achtung

:::warning[Achtung]
<Misconception id="m16-l10-dbcontext-as-singleton" />

**„Ein `DbContext` sollte als Singleton registriert werden, weil das Erzeugen teuer ist.“** Ein Context ist für eine kurze Arbeitseinheit gedacht, trägt Zustand (verfolgte Objekte) und ist nicht thread-sicher. `AddDbContext` registriert ihn als Scoped-Service.
:::

:::warning[Achtung]
<Misconception id="m16-l10-parallel-queries-one-context" />

**„Mit `Task.WhenAll` kann ich mehrere Abfragen auf demselben Context parallel ausführen.“** Ein Context erlaubt nur eine Operation zur Zeit. Für parallele Arbeit brauchst du je einen Context.
:::

<details>
<summary>Vertiefung: Context-Pooling (optional)</summary>

`AddDbContextPool` ist eine Variante von `AddDbContext`, die Context-Objekte wiederverwendet, statt sie jedes Mal neu zu erzeugen. Sie gehört zu den Themen der Leistungsoptimierung. Für SecLog brauchst du sie nicht, Einzelheiten stehen bei [Advanced Performance Topics](https://learn.microsoft.com/ef/core/performance/advanced-performance-topics).

</details>

## Zusammenfassung

Datenbankaufrufe sind Ein-/Ausgabe: Du nimmst die `Async`-Varianten, wartest sie ab und gibst ein `CancellationToken` weiter. Ein `DbContext` ist eine kurze, nicht thread-sichere Arbeitseinheit. `AddDbContext` registriert ihn als Scoped-Service. Ein Singleton oder Hintergrunddienst erzeugt einen Scope pro Arbeitseinheit oder nutzt `IDbContextFactory<T>`. Zwei gleichzeitige Operationen brauchen zwei Contexts.
