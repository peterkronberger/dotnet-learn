## Ein Fremdschlüssel verbindet zwei Tabellen

Ein Vorfall besteht aus mehreren fehlgeschlagenen Anmeldungen. Mit einer Tabelle allein geht das nicht: Eine Spalte hält pro Zeile nur einen einfachen Wert, keine Liste. Die Datenbank löst das mit zwei Tabellen. Die Tabelle `Events` bekommt eine Spalte, die den Schlüssel des Vorfalls enthält. Eine solche Spalte heißt <Term id="foreign-key">Fremdschlüssel</Term>: Sie zeigt auf den Primärschlüssel einer anderen Tabelle ([Introduction to relationships](https://learn.microsoft.com/ef/core/modeling/relationships)).

Die Tabelle, auf die gezeigt wird, ist die **Prinzipal-Seite** (principal): `Incidents`. Die Tabelle mit dem Fremdschlüssel ist die **abhängige Seite** (dependent): `Events`.

In den Klassen bildest du das mit <Term id="navigation-property">Navigationseigenschaften</Term> ab:

- Eine **Referenz-Navigation** zeigt auf ein Objekt: `Event.Incident`.
- Eine **Collection-Navigation** zeigt auf eine Liste: `Incident.Events`.

Heißt der Fremdschlüssel `<Navigation>Id`, hier `IncidentId`, erkennt EF Core die <Term id="one-to-many-relationship">1:n-Beziehung</Term> per Konvention, ohne weitere Konfiguration ([One-to-many relationships](https://learn.microsoft.com/ef/core/modeling/relationships/one-to-many)).

Das folgende Programm druckt die Tabellen, speichert zwei Vorfälle mit ihren Events und zählt die Events je Vorfall. Die Zählung braucht keine zusätzliche Anweisung zum Laden: Die Datenbank zählt selbst.

<summary>Lösung und Erklärung anzeigen</summary>

<CodeBlock language="sql" title="Ausgabe">{oneToManyOutput}</CodeBlock>

1. **Spalte:** `IncidentId` ist `INTEGER NOT NULL` und die Spalte für den Fremdschlüssel.
2. **Regel:** `FOREIGN KEY ("IncidentId") REFERENCES "Incidents" ("Id")` heißt: Jeder Wert in `IncidentId` muss als `Id` in `Incidents` vorkommen. `FOREIGN KEY` nennt die Spalte, `REFERENCES` die Spalte der anderen Tabelle.
3. **Index:** EF Core legt für den Fremdschlüssel einen Index an, damit die Events eines Vorfalls schnell gefunden werden.
4. **Pflicht:** `NOT NULL` macht die Beziehung zur Pflicht: Ein Event ohne Vorfall gibt es nicht.

`ON DELETE CASCADE` heißt: Wird ein Vorfall gelöscht, löscht die Datenbank seine Events mit (Cascade Delete, [Cascade delete](https://learn.microsoft.com/ef/core/saving/cascade-delete)).

**Was passiert, wenn …** du `IncidentId` als `int?` und `Incident` als `Incident?` schreibst? Dann ist die Spalte `NULL`-fähig und die Beziehung optional: Ein Event darf ohne Vorfall existieren.

</details>

## Die Fluent API für Beziehungen

Passt die Konvention nicht, legst du die Beziehung in `OnModelCreating` fest. `HasOne` wählt die Referenz-Navigation, `WithMany` die Collection-Navigation der Gegenseite, `HasForeignKey` den Fremdschlüssel. Eine 1:1-Beziehung gibt es auch (`HasOne` mit `WithOne`). Sie kommt in diesem Kurs nicht weiter vor.

## n:m ohne eigene Klasse

Ein Vorfall wird von mehreren Analysten bearbeitet, und ein Analyst bearbeitet mehrere Vorfälle. Das ist eine <Term id="many-to-many-relationship">n:m-Beziehung</Term>. Eine einzelne Fremdschlüssel-Spalte reicht dafür nicht. In EF Core bekommen beide Klassen eine Collection-Navigation auf die andere. Eine <Term id="join-table">Verbindungstabelle</Term> mit je einer Zeile pro Zuordnung legt EF Core selbst an ([Many-to-many relationships](https://learn.microsoft.com/ef/core/modeling/relationships/many-to-many)).

1. **Tabellen:** `Analysts` und `Incidents` für die Klassen, dazu `AnalystIncident` für die Zuordnung.
2. **Spalten:** `AnalystIncident` hat nur zwei Spalten, `AnalystsId` und `IncidentsId`. Beide sind Fremdschlüssel.
3. **Schlüssel:** Der Primärschlüssel besteht aus beiden Spalten. Dieselbe Zuordnung kann es darum nur einmal geben.
4. **Ergebnis:** Der Analyst `alice` ist mit zwei Vorfällen verbunden, `alice: 2`.

Die Navigationen, die EF Core für die Verbindungstabelle benutzt, heißen Skip-Navigationen: Du gehst über die Tabelle hinweg, ohne sie zu sehen.

**Was passiert, wenn …** die Zuordnung eigene Daten tragen soll, zum Beispiel den Zeitpunkt der Zuweisung? Dann schreibst du eine eigene Verbindungsklasse mit den beiden Fremdschlüsseln und dieser Eigenschaft.

</details>

## Projektschritt

**Stand bisher:** SecLog (`_ci/seclog-m16-l02/`) speichert die Vorfälle in einer SQLite-Datenbank mit konfiguriertem Schema. Die Fehlversuche selbst werden noch nicht gespeichert.

**Neue Anforderung:** SecLog speichert zu jedem Vorfall auch die fehlgeschlagenen Anmeldungen, aus denen er besteht. Lege dafür die Klasse `StoredEvent` mit dem Fremdschlüssel `StoredIncidentId` an, ergänze die Collection-Navigation `Events` in `StoredIncident` und gib unter `== Database ==` die Zahl der gespeicherten Events je Vorfall aus. ## Achtung

:::warning[Achtung]
<Misconception id="m16-l03-many-to-many-needs-join-class" />

**„Für eine n:m-Beziehung muss ich immer eine eigene Verbindungsklasse schreiben.“** Zwei Collection-Navigationen genügen. EF Core legt die Verbindungstabelle selbst an. Eine eigene Klasse brauchst du nur, wenn die Zuordnung eigene Daten hat.
:::

## Zusammenfassung

Ein Fremdschlüssel ist eine Spalte, die auf den Primärschlüssel einer anderen Tabelle zeigt. Bei einer 1:n-Beziehung trägt die Seite „n“ den Fremdschlüssel. In den Klassen stehen eine Referenz-Navigation dort und eine Collection-Navigation auf der Gegenseite. Ein nullable Fremdschlüssel macht die Beziehung optional. Bei n:m genügen zwei Collection-Navigationen, und EF Core legt eine Verbindungstabelle mit zwei Fremdschlüsseln an. `GenerateCreateScript()` zeigt das Ergebnis.
