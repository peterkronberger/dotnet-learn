## Dasselbe Lambda, zwei Umwandlungen

In `m16-l04` hat EF Core Lambdas wie `i => i.FailureCount >= 5` nicht aufgerufen, sondern gelesen. Das geht, weil ein Lambda auf zwei Arten umgewandelt werden kann. Es passt zu einem Delegaten-Typ wie `Func<Incident, bool>`: Dann ist es ausführbarer Code. Es passt auch zu `Expression<Func<Incident, bool>>`: Dann ist es ein <Term id="expression-tree">Ausdrucksbaum</Term>, also eine Datenstruktur, die den Aufbau des Lambdas beschreibt ([Expression tree types, §8.6](https://learn.microsoft.com/dotnet/csharp/language-reference/language-specification/types#86-expression-tree-types)). Welche Umwandlung gilt, bestimmt der Typ, dem das Lambda zugewiesen wird.

Das folgende Programm wandelt dasselbe Lambda auf beide Arten um. Es braucht kein Paket und keine Datenbank.

<summary>Lösung und Erklärung anzeigen</summary>

<CodeBlock language="text" title="Ausgabe">{expressionTreeOutput}</CodeBlock>

1. **Aufrufen:** Der Delegat lässt sich nur aufrufen: `asDelegate(bob)` ergibt `True`. Wie er aufgebaut ist, kann das Programm nicht fragen.
2. **Lesen:** Der Baum ist Daten. `ToString()` gibt das Lambda als Text aus, `Parameters` nennt den Parameter `i`, `Body` den Rumpf, und `NodeType` zeigt die Art des obersten Knotens: `GreaterThanOrEqual` ist der Vergleich `>=`.
3. **Umwandeln:** `Compile()` baut aus den Daten einen Delegaten. Erst dann läuft der Code, und das Ergebnis ist wieder `True`.

**Was passiert, wenn …** du dem Lambda einen Block mit `{ … }` gibst? Dann lässt es sich nicht mehr in einen Ausdrucksbaum umwandeln: Nur Ausdrucks-Lambdas (`x => ausdruck`) gehen, Anweisungs-Lambdas nicht ([Anonymous function conversions, §10.7.3](https://learn.microsoft.com/dotnet/csharp/language-reference/language-specification/conversions#1073-evaluation-of-lambda-expression-conversions-to-expression-tree-types)). Auch `async` und eine Zuweisung im Lambda gehen nicht.

</details>

## IQueryable sammelt, IEnumerable führt aus

<Term id="iqueryable">`IQueryable<T>`</Term> ist eine Abfrage, die als Ausdrucksbaum vorliegt. Ihre Eigenschaft `Expression` hält diesen Baum, und `Provider` ist der <Term id="query-provider">Abfrage-Provider</Term>, der den Baum auslesen kann. Bei EF Core ist das der Datenbank-Provider, der den Baum in SQL übersetzt. Ein `DbSet<T>` ist ein `IQueryable<T>`.

Die Methoden unterscheiden sich im Parameter. `Queryable.Where` nimmt einen `Expression<Func<T, bool>>`: Das Lambda bleibt Daten und wird an den Baum angehängt. `Enumerable.Where` nimmt einen `Func<T, bool>`: Das Lambda ist Code und läuft für jedes Element im Speicher. Welche der beiden Methoden der Compiler wählt, hängt vom Typ links vom Punkt ab ([`IQueryable<T>`](https://learn.microsoft.com/dotnet/api/system.linq.iqueryable-1)).

Das folgende Programm filtert viermal dasselbe, aber mit anderen Typen. Es druckt jeden Befehl, der an die Datenbank geht. Die Hilfsklasse am Ende ist eingeklappt.

1. **`IQueryable`:** `db.Incidents` ist ein `IQueryable<Incident>`. `Where` ist `Queryable.Where`, der Filter steht als `WHERE` im SQL, und nur eine Zeile kommt an.
2. **`IEnumerable`:** Die Variable hat den Typ `IEnumerable<Incident>`. Damit ist `Where` die Methode `Enumerable.Where`: Das SQL hat kein `WHERE`, alle Zeilen werden geladen, und das Programm filtert danach.
3. **`AsEnumerable`:** Der Teil vor `AsEnumerable()` wird übersetzt (`WHERE … >= 1`). Alles danach läuft im Speicher. Die Bedingung `i.User.Length == 3` steht deshalb nicht im SQL.
4. **`ToList` zu früh:** `ToList()` führt die Abfrage sofort aus und lädt alle Zeilen. Das spätere `Where` arbeitet auf einer Liste, nicht auf der Datenbank.

In allen vier Fällen ist das Ergebnis dasselbe: eine Zeile bleibt übrig. Der Unterschied liegt darin, wo gefiltert wird. Mit 3 Zeilen merkst du ihn nicht, mit Millionen Zeilen schon.

**Was passiert, wenn …** du das `ToList()` am Ende von Abschnitt 1 weglässt? Dann geht der Befehl erst beim Auslesen los. Der Filter steht trotzdem im SQL, denn er hängt am `IQueryable<T>`.

</details>

## Was EF Core nicht übersetzen kann

EF Core kann einen Ausdrucksbaum nur übersetzen, wenn es für jeden Teil SQL kennt. Eine eigene C#-Methode kennt es nicht: Im Baum steht nur ihr Aufruf, nicht ihr Rumpf. Steht sie in `Where`, löst EF Core eine `InvalidOperationException` aus. Nur in der letzten `Select`-Projektion erlaubt EF Core Code, den es nicht übersetzen kann: Es liest die nötigen Spalten aus der Datenbank und ruft die Methode danach im Programm auf. Dieses Auswerten im Programm heißt <Term id="client-evaluation">Client-Auswertung</Term> ([Client vs. server evaluation](https://learn.microsoft.com/ef/core/querying/client-eval)).

## Achtung

:::warning[Achtung]
<Misconception id="m16-l05-tolist-at-end-changes-nothing" />

**„`ToList()` am Ende einer Abfrage ändert nichts.“** `ToList()` führt die Abfrage aus. Und die Stelle bestimmt, was in der Datenbank läuft: Alles vor `ToList()` kann in SQL übersetzt werden, alles danach läuft im Speicher auf den schon geladenen Zeilen.
:::

:::warning[Achtung]
<Misconception id="m16-l05-ef-translates-every-method" />

**„EF Core schickt jede LINQ-Methode und jede C#-Methode an die Datenbank.“** EF Core übersetzt nur, wofür es SQL kennt. Eine eigene Methode in `Where` löst eine `InvalidOperationException` aus. Nur in der letzten `Select`-Projektion läuft sie im Programm.
:::

## Zusammenfassung

Ein Lambda ist je nach Zieltyp Code (`Func<…>`) oder Daten (`Expression<Func<…>>`). `IQueryable<T>` sammelt diese Daten, damit der Provider sie in SQL übersetzen kann, und `Queryable.Where` nimmt einen Ausdrucksbaum. `IEnumerable<T>` führt das Lambda im Speicher aus, und `AsEnumerable()` wechselt bewusst dorthin. Eigene C#-Methoden in `Where` lassen sich nicht übersetzen. Nur im letzten `Select` läuft Code im Programm.
